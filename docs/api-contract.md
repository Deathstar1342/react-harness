# Integration contract

## M28–M32 deployment boundary

[CONTAINERIZATION.md](../CONTAINERIZATION.md) defines the new deployment target. Preserve existing native tool/runtime API semantics; add separate typed host-path, managed-project and container-path identities. The trusted host launcher alone handles local engine lifecycle and native file transfers. A container service cannot use project import or worker execution to request arbitrary host filesystem/engine access. M28 proposes concrete storage/readiness/auth contracts; M29 proposes bounded owned execution/install claims and result/cleanup semantics; M30 proposes one-time transfer publication/export; M31 integrates Electron IPC. Document each accepted interface here at delivery. Existing APIs below remain implementation descriptions until superseded; no automatic sync/write-back API is planned. Backend secrets and Docker control never enter agent shells or renderer payloads.

## M25 scoped instructions, files and processes

`readProjectInstructions(tools,root,targets)` loads root AGENTS.md plus the canonical ancestor chains of current assignment, requested and previously observed paths. Directory targets include their own AGENTS.md. Rename combines source and destination chains. No recursive repository walk or unrelated sibling discovery occurs. Broad planning/discovery/shell actions receive root plus the declared/known chains; this is explicitly **known-scope coverage**, not proof that all project instructions were discovered. Bounds: 100 retained targets per task, depth 16, 256 candidate paths, 32 present files, 32,000 UTF-8 bytes per file and 128,000 aggregate bytes. Protected paths, links, invalid encoding and overflow fail closed with a narrower-scope error. Missing and empty remain distinct. The effective revision hashes ordered present path/status/hash tuples plus root absence; discovering another absent chain alone does not invalidate proposals, but every candidate is reread to detect creation. Runtime/human priority remains above guidance; nearer ancestors override conflicting parent text only in their subtree. Repository text cannot change roles, native provenance, permissions, installations or completion authority.

Guidance remains outside compactable history and is refreshed before model calls, after inspection/approval awaits, at dispatch and at review/goal acceptance. A newly applicable guidance revision cancels unstarted calls with correlated results, invalidates approvals and goal reviews, and regenerates proposals. Changes/failures stop owned live jobs without implying rollback. `maintain_instructions` is architect-only and execution-only: canonical AGENTS.md paths, fresh baseHash and bounded line patches through the ordinary diff/lease/approval/history path. Planning can draft prose only. Guidance describes structure, commands, conventions and durable decisions; objectives/progress stay in goal storage.

| Native tool | Arguments and observed result |
| --- | --- |
| `read_file_range` | `{path,startLine,count}`; one-based start, count 1–500, at most 64,000 output bytes. Returns literal content, whole-file hash, totalLines and nextLine. Existing text-file read bounds still apply. |
| `search_page` | `{query,path?,offset?,limit?,revision?}`; literal query, offset ≤10,000, limit ≤100. Subsequent pages require the returned revision, which binds query/path and observed file/listing hashes. Returns matches, revision, nextOffset, observedMatches and incomplete. Text excerpts are at most 500 characters. |

| `maintain_instructions` | Same patch arguments, canonical basename AGENTS.md only, architect execution mode only, final file ≤32,000 bytes. No arbitrary architect file/shell capability. |
| `delete_file` | `{path,baseHash}` with a present hash. Full deletion diff; fresh version, confined regular file, final inode/hash and dirty lease checks. |
| `rename_file` | `{path,destination,baseHash}`; present source, absent distinct destination, both paths in assignment scope. Two-path diff and one coherent history operation. |

| `cancel_process` | `{processId}`; exact owning coder frame only, execution mode. Stops an already-authorized handle without new approval and awaits observed cleanup. Critics cannot cancel. |

Search is a bounded observed traversal: at most 2,048 entries, depth 8, 8 MB text, 10,000 matches and two seconds, plus existing directory/file ceilings. Fixed dependency/build directories are omitted unless directly targeted; protected/link/binary/unreadable entries are excluded. `incomplete` reports observed coverage limits and omitted dependency/readable-text coverage, not proof of absence. A time-limited observation can differ between pages without a source edit; the error explicitly asks for a narrower scope rather than proving a change. There is no filesystem snapshot guarantee.

File inspection adds optional `changes:[{before:FileSnapshot,after:FileSnapshot}]`, at most two, with a 200 KB diff bound. Rename is a guarded **copy/remove**, not atomic OS rename: sorted project/file reservations and both leases, source hash/inode, durable operation claim, possible parent creation, exclusive `wx` destination creation, source-mode/content write and fsync, repeated source/destination hash/inode/lease checks, then source unlink. No overwrite-capable rename or uncertain cleanup is used. Partial directories/files survive as unknown evidence; external filesystem race freedom and full metadata preservation are not claimed. Genuine pre-effect collision remains not_started. Once an effect is possible, failure is uncertain.

`FileChange.destination?` stores paired before/after snapshots privately; public `FileChangeSummary.destinationPath?` shows the move. Patch/delete/maintenance share normal history. Undo preview checks both current paths; move undo reverses the guarded operation only with original source absent and exact destination. Its transactional claim precedes parent/file creation. Partial undo becomes unknown and is never retried. Undo POST `expectedHash` now permits null for deleted/moved source paths, still bound to the exact expiring preview token. Both path viewers receive change events. Existing records remain readable; no profile migration is introduced.

Process records use existing private SQLite state and retain project/chat/root-task/frame/original native-call/pending-command identities, generation/mode/approval/plan/assignment/guidance/goal bindings. A single-use `starting` claim commits before sandbox setup. After setup awaits, the executor refreshes applicable guidance and synchronously revalidates all durable identities/reservation/cancellation, then commits `running` intent immediately before PTY dispatch. The private Symbol reservation/callbacks never enter model/browser arguments, records or child environments. Unsupported executors fail closed. The command runs in the existing Linux Bubblewrap PTY with a dedicated logical session; there is no host fallback, PID adoption or second coder scheduler.

A shared synchronous reservation is acquired before asynchronous mutation work by file/editor/undo operations, regular command queues, managed processes, install advancement/recovery, reset and removal. Only the private owner can enter its underlying command while reserved. Reads remain available. Ordinary same-session commands retain their serialized queue. Active/uncertain jobs block incompatible mutations and whole-goal acceptance. Active jobs or unconfirmed cleanup block frame completion/review. After confirmed cleanup, interrupted/uncertain work may be submitted as failure/limitations, but its independent review cannot accept it; the blocker returns to the architect without automatic repair/replay. Critic PASS and status reads cannot clear uncertainty. Process-start success does not create a JUnit report or satisfy prior failed verification.

Terminal states are completed (observed exit 0), failed (observed failure), not_started (no dispatch acknowledgment), interrupted (observed cancellation/timeout after dispatch) and uncertain (lost boundary, descendants, persistence or cleanup). Dedicated namespace/broker teardown must finish before the reservation releases. Explicit pause/interrupt/steering/close abort owned jobs; ask_user and approval waits do not themselves cancel authorized jobs. Output/final callbacks only persist observations, never schedule models or mutate frame calls. The original start native call gets its own result; later observations have separate correlated calls. Restart marks claimed nonterminal jobs uncertain, retains evidence and never replays, adopts or signals a saved PID. Persistence failure aborts the private controller and cannot later become success. Cleanup failure retains backend ownership.

Each project permits at most 64 retained process handles, with no silent eviction or Resume reset; once reached, synchronous commands remain available if there is no uncertain job. Each job retains at most 64,000 output bytes, at most 128 streamed output events, and bounded final event snapshots; no full duplicate ToolResult is archived. Backend-key redaction spans chunk boundaries. Arbitrary secrets embedded in ordinary source remain outside filename-based protection. Public handles contain no OS PID, environment, callback or capability. Architect observations are limited to assigned frames in the same root task; critics to the explicit reviewed frame; coders to their own frame. Existing authenticated API `POST /api/chats/:id/processes/:processId/cancel` with `{}` provides exact-chat human cancellation; Terminal exposes only that Stop control, no command input. A stale/unknown handle cannot acquire a capability.

There is deliberately no generic process-uncertainty reconciliation API. A retained uncertain job keeps that project's mutation/completion/removal gates closed; Resume, model review or cancellation cannot erase it. Original evidence is retained for human inspection. Existing narrowly authenticated install reconciliation remains the sole supported helper uncertainty resolution and is unchanged in authority.

## M24 durable goals

`ChatDetail.goal?: Goal` and durable `goal` SSE events expose current intent/status, criteria with stable IDs and evidence kinds, cumulative required step titles/identities, accepted review/tool references, budgets, reasons, uncertainty and visible superseded human revisions. `GET /api/chats/:id/goal` returns `{goal: Goal|null}`. `POST` to that path accepts strict `{objective,acceptanceCriteria:string[],observationCriteria?:number[]}` and returns the created Goal with HTTP 202. `PATCH` additionally requires `expectedRevision` and a nonblank `reason`; it explicitly supersedes old scope and returns 409 for stale revision. A second POST or `/goal` cannot silently replace a goal. Provider configuration is required for create/revise because these submit human intent to the runtime. Existing origin/JSON/access policies apply.

Objective is trimmed and bounded to 16,000 UTF-8 bytes; 1–32 criteria each have 1–4,096 bytes, are trimmed and must be distinct. Optional `observationCriteria` contains unique zero-based in-range indexes; workspace evidence is the default. IDs are reused only for exactly equal normalized criterion text and evidence kind (case-sensitive). A revision may reorder unchanged criteria without erasing known obligations. At most 32 revisions and 256 cumulative required steps are supported; exceeding bounds fails explicitly. Historical scope/reasons remain visible in the panel. The existing SQLite JSON state table is used; no old-profile migration or new service is introduced.

`/goal <objective>` records that explicit objective as its default single criterion. Additional newline `- <criterion>` lines supply explicit acceptance criteria. `- [observation] <criterion>` is the literal human opt-in to historical read-only evidence; the marker requires a delimiter, and an empty marked criterion is rejected. `[observation]suffix` is ordinary workspace criterion text. Ordinary chats remain conversational. `/goal` while already planning records intent but does not authorize execution; exact Start building or existing explicit build intent remains necessary. `/btw` preserves requirements and invalidates current acceptance; it does not resume a paused/blocked goal. An answer to `ask_user` continues within the existing quota. Resume explicitly renews quotas; approval decisions do not.

`delegate` adds optional `goal:{goalId,goalRevision,criterionIds}` and `evidenceKind:'workspace'|'observation'`. Active goals require a current exact goal reference, unique valid criterion IDs and current `planStep`. Observation is accepted only when every mapped human criterion explicitly permits it. Any attempted mutation/test/install, failed read or missing terminal read evidence disqualifies observation-only acceptance. Observation evidence states historical read results, not current source stability. Mixed assignments use workspace verification. Model mappings and critic judgments are evidence about semantics, not proof that arbitrary prose criteria have been fulfilled.

Architect-only, execute-only, terminal `request_goal_completion` requires `{goalId,goalRevision,planId,planVersion,modeVersion,reviewEventIds}`. IDs must be exactly the current runtime-accepted review set with no duplicates. The gate checks every original/current required step, each criterion's reviewed assignment, exact current plan progress, recorded tool/review references, private original assignment, known verification obligations and uncertainty. Removing/renaming steps via `set_plan` never removes obligations; human scope revision is the only supersession route. Every awaited freshness check rechecks run/goal generations, frame/call, mode and goal/plan revisions, with a final repeat inside the cloned COMMIT transition. Accepted workspace scopes use the existing 128-entry/depth-8/1-MB/two-second confined snapshots and a five-second aggregate final-check bound. Unknown/changed scope rejects completion. Source checks do not establish outside-scope dependencies, filtered files, shell cwd/environment, report authenticity or race freedom.

Private `goal-evidence:<chat>` records minimal original assignment/binding and scope metadata, without duplicating full Frame/history/testcase ledgers. `goal-obligations:<chat>` keeps bounded verification ledgers after frames are popped. Matching goal/criterion/step/path assignments inherit unresolved checks; criterion/path order is normalized for binding. Unrelated accepted work cannot clear failed checks. A human revision retaining any affected criterion retains the conservative obligation (including mixed bindings); explicitly removed criteria remain in superseded history. Changing the plan mapping does not clear a retained check. Original tool/check events remain immutable. Uncertainty persists across revisions, restarts and verdicts, including helper `uncertain`/`recoveryRequired` outcomes. The bounded public uncertainty view retains 100 IDs; overflow remains explicitly blocked, with original events in the archive. This milestone supplies no automatic uncertainty reconciliation or replay.

Goal states are `running`, `waiting_for_approval`, `waiting_for_user`, `paused`, `blocked`, `completed`, each with a reason. Completion, waits, human controls and budget stops persist with the native run/history in transactions; cached frames publish only after COMMIT. One existing serialized loop owns continuation; no second mutating worker exists. Limits per explicit continuation are 128 provider dispatches, 256 model/queued-action loop transitions and 16 model turns without a newly accepted required step. Pending-action settlement polls do not count as provider dispatches. Compaction remains separately covered by the existing account scheduler. The no-progress limit is intentionally conservative: a useful long assignment can pause and need human Resume. Quota exhaustion never means completion. Budget counters survive restart; approval, prose and autonomous continuation cannot reset them. Backend close/recovery pauses active goals, cancels obsolete proposals, preserves correlated history and blocks dispatched uncertainty; constructing the app/runtime never launches goal work.

Model controls include active protected requirements, current evidence references, remaining scope and blockers. Superseded histories and private testcase matching ledgers stay out of summaries/model context. Oversized protected active scope fails visibly rather than being silently truncated. The compact Goal/status/phase indicator opens the existing collapsible panel; criteria, reasons, evidence limits, quota and explicit scope revision appear there.

Goal verification storage additionally caps total retained checks at 256 and testcase identities at 10,000 across bindings; overflow records a durable unverified gate instead of losing obligations silently. Colliding mixed bindings after a human revision retain the union of required testcase coverage and require re-verification. The goal edit form snapshots `expectedRevision` when opened. SSE updates do not advance that token: a concurrent human revision returns 409, retains the draft and requires explicit reopening/review. The phase indicator counts current goal-accepted reviews, not stale plan progress from an earlier goal revision.

The only supported uncertainty resolution is an exact existing system-install recovery, never generic shell/file reconciliation. After the existing explicitly human-invoked `InstallService.recover` authenticates the helper target and validates its exact request/preview, one transaction rechecks the current local install identity/state/target/preview/recommendation and commits the outcome, private `install-reconciliation:<requestId>` receipt and `install_reconciliation` event. The private receipt binds request ID, chat, canonical target, preview digest, method (`status`/`reconcile`), outcome and event ID. Goal creation can recognize a previously validated receipt; an existing blocked goal applies resolutions only on explicit Resume. No helper call, replay, launch or quota reset is triggered by receipt creation.

Resolution requires the exact linked original tool/recovery event, current install and selected target matching that receipt, `succeeded`, `healthy=true`, `matches=true`, and `recoveryRequired=false`, plus the actual recorded recovery event. Merely healthy nonmatching/uncertain results, missing/stale/mismatched receipts, arbitrary local terminal-status changes and generic/ambiguous effects remain blocked. `Goal.resolvedUncertainties` contains only `{eventId,installId,reconciliationEventId}`; private target/preview bindings and capabilities never enter model/public goal payloads. Original uncertain IDs/events remain unchanged. Union/overflow handling is shared by coder, architect, historical creation and restart paths. Receipt/COMMIT failure rolls back outcome and resolution publication; only another explicit status/reconcile can retry observation, never install execution.

## M23 private prompt and assignment contract

`server/prompts.ts` exports `roleInstructions(role, extension?)`, `PROMPT_VERSIONS` and `promptIdentity(systemText)`. `server/protocol.ts` is removed; there is no legacy prompt/parser adapter. Extensions remain backend-only bounded UTF-8 files (32,000 bytes); composition enforces the same byte bound and does not grant tools or permissions. Native argument/result schemas stay in the registry; existing HTTP and shared DTOs are unchanged.

Private `RunState.humanMessageIds` identifies stored human turns for the current task and steering. Only those stored `role:user` messages enter the human-constraint section; internal user-shaped feedback and repo/summary text cannot acquire that provenance. Planning-to-building retains the original task's IDs. Private `Frame.assignment` stores `{objective,acceptanceCriteria,paths?,planStep?}` copied from validated delegation arguments; it is architect-authored context, not approval. Completion/checkpoint critics receive that original snapshot. Current association remains separate and can be invalidated by steering without erasing original criteria. No strings or model-written evidence references are interpreted as authority.

`Frame.acceptanceEvidence` is a bounded private ledger updated with actual tool event IDs in the native result clone/COMMIT transition. It tracks up to 100 exact canonical argument digests for `run_tests` and 100 uncertain/interrupted effect events, with a global 10,000 hashed testcase-identity bound; overflow blocks acceptance. Matching complete verification may replace a failed/missing/stale check, preserving historical events. Observed classname/name multiplicity cannot shrink; previously non-skipped identities must actually pass, while ordinary optional skips may coexist with a nonempty passing suite. A changed command, report path or other argument does not clear an earlier check. A passed check is stale after later possible write/shell/Python mutation. Test commands also carry private before/after `VerificationSnapshot` data from confined explicit-scope read/list (128 entries, depth 8, 1 MB, two seconds). Unknown/changed scope cannot establish verification freshness. Stable independent checks coexist; completion review refreshes the same scope and rechecks frame/generation/mode/assignment bindings after awaits. Only the fixed default report path is excluded. Scoped snapshots do not establish whole-workspace stability, persistent cwd/environment equivalence, test authenticity or immunity to external races. Argument matching is deliberately exact, including timeout and report path; changed arguments cannot resolve prior ambiguous check obligations. Exit zero with missing/empty/all-skipped/error report remains incomplete verification, not a fabricated nonzero exit. The completion reviewer may retain its raw PASS verdict, but the matching plan step remains blocked while these runtime blockers exist. Repairs are bounded; uncertainty is not automatically retried or reconciled. Read-only work can still be accepted with recorded evidence and independent review; ordinary nonzero discovery is not assumed to be a required test.

`reviewKind` distinguishes `checkpoint`, `completion` and `independent` internally. Checkpoints cannot finish assignments; an independent architect-requested review cannot accept unrelated plan steps. `submit_completion` ends an ordinary architect frame or sends a coder to review. In an active executing M24 goal, architect frame completion instead continues remaining work within its budget; only the separate goal gate can complete the goal.

Private `context:prompt:<chat>:<frame>:<step>` records the exact system prompt digest, module versions, role/model, generation and guidance hash immediately before the role request. It contains no extension text or path and is not returned by settings/events. Required original human/assignment context is not silently truncated to fit; context-budget errors remain explicit. Transcript excerpts and continuation summaries are separately labelled untrusted, with native groups preserved.

## M19 system install policy and history

- GET `/api/system-installs/settings` -> `InstallSettingsView`: policy `ask|auto|ai`, reviewerModel, monotonically increasing revision, optional authenticated target, availability/message and scope `current-profile-local-linux-target`. Checks an existing helper lazily; no provisioning/startup action. Missing/unsupported helpers leave ordinary APIs available.
- PATCH the same path with strictly `{revision,policy?,reviewerModel?}`. Revision is required for optimistic concurrency. Models are bounded exact IDs; default is copied once from the initialization-time critic. Settings are stored in the current profile database under `system-installs:v1`; workspace preferences/chat models remain independent. Target is never supplied by HTTP/model. A changed authenticated local target increments revision, resets Ask and invalidates old decisions.
- Native `recommend_packages` strictly `{packages:[{name,version?}],reason}`: 1–16 unique apt names, optional exact versions, reason <=2000 characters. Only architect/coder in execute mode. No executable/options/command/path/env fields. It is not a workspace tool; workspace approve-all cannot authorize it.
- Ask/fallback creates an ordinary `Approval` with additive `install:InstallRecord` containing public concrete evidence. POST `/api/approvals/:id` still accepts only `{decision:'approve'|'deny'}`. Backend binds the decision to the exact helper request/preview/expiry, policy revision, reviewer, target, role/frame/generation/mode version. Renderer supplies no helper authorization data. Exact helper expiry is two minutes; the UI disables expired decisions and offers a fresh request.
- POST `/api/system-installs/:id/refresh`, strictly `{}`, creates a NEW UUID/request/preview/decision only for a still-associated stale/failed frame. It does not transfer prior approval. Superseded context returns 409 and requires a new recommendation in the chat.
- GET `/api/system-installs/history` -> `{items:InstallRecord[],truncated:boolean}` returns the newest 100 profile records on demand, including retained records for removed chats/projects. No helper nonce/descriptor/key or private reviewer context is projected.
- POST `/api/system-installs/:id/status` or `/reconcile`, strictly `{}`, queries the original helper request. No execute retry. Unavailable/original-target mismatch retains recovery protection. Explicit healthy reconciliation can clear the gate while retaining original `uncertain` outcome and separate observed package versions/health. The endpoint cannot fabricate success.

All routes retain loopback host/origin/JSON protections. IDs resolve server-owned records; extra authority fields reject. Additive SQLite `install_requests(id,project_id,chat_id,data)` has no cascading foreign key. Pending/active/recovery-required records protect scoped deletion; terminal history is retained. Expiry/policy changes stale pre-dispatch approvals, pause an awaiting chat, and never release old work. Shutdown drains live local calls, preserves uncertainty, and restores the recovery gate on next startup without replay or permanently blocking close for historical uncertainty.

States: `preparing -> reviewing/pending/approved -> authorizing -> dispatching -> succeeded/failed/uncertain`; noop, rejected and stale are explicit. Creation precedes helper prepare; dispatch intent precedes execute. The final current-binding check, persisted dispatch claim and immediate helper execute invocation do not yield. Settings/cancel/mode/steering transitions invalidate before that boundary; after it, apt is not undone. Restart stales undecided work and marks abandoned authorizing/dispatching as uncertain for status/reconciliation only.

Install review uses fixed separate guidance and curated target/package/impact/reason data (<=64 KB), a 20-second bound, 1024 output tokens and the existing managed critic account ledger. It accepts exactly one native `install_decision` call with two unique argument fields `decision:approve|reject|ask` and `reason` <=400 characters; malformed/duplicate/extra/refused/unavailable/timed-out answers become human approval if still fresh. No raw review response or full transcript is stored. Additive trusted `ModelProvider.complete.noRetry?:boolean` disables retries for this call only, propagates through existing hooks/ReloadingProvider, and is never an upstream JSON field. Ordinary transport defaults are unchanged.

## M18 trusted package helper

Additive `PackageHelperTarget/Request/Preview/Decision/Record` DTOs in shared/types.ts and backend-only `PackageHelperClient` in server/package-helper.ts. No HTTP route, model action or UI authority is added. `connect()` reads only the root-owned fixed descriptor for the current non-root Linux UID. `hello()` authenticates the target and installed helper identity. `prepare(request)`, `authorize(decision)`, `execute(decision)`, `status(requestId)` and `reconcile(requestId)` are explicit trusted calls with no automatic retry or elevation. See [helper setup/security/recovery](helper.md).

Wire v1 is one bounded UTF-8 JSON line on `/run/abyssus-helper/control.sock`. Request object is strictly `{protocol:'abyssus-helper-v1',nonce,expiresAt,action,body,mac}`. Nonce is 32 random bytes in lowercase hex; expiry is integer epoch milliseconds within 30 seconds. MAC is HMAC-SHA256 using the descriptor key as UTF-8 over recursively key-sorted compact ASCII-escaped JSON of the object excluding `mac`. Duplicate keys, extra fields, oversized/multiple lines, wrong peer UID, bad version/MAC, expired envelope and reused nonce reject. Helper persists authenticated envelope nonces across restart until expiry. Responses use the same canonical MAC over `{protocol,nonce,ok,result}` or `{protocol,nonce,ok,error}`; errors are fixed codes. Client reply limit is 256 KiB and timeout five minutes; timeout/disconnect has no cancellation or retry semantics.

`prepare` body: `{requestId:UUID,targetId:hex64,manager:'apt',packages:[{name,version?}]}`. `authorize` and `execute`: `{requestId,previewDigest:hex64,decisionNonce:hex64,expiresAt}`. Hello uses `{}`; status/reconcile use `{requestId}`. Decision expiry cannot exceed the prepared record's two-minute lifetime. Names/versions are restricted identities, never options, paths or shell. Omitted version resolves then pins the candidate. DTO states are prepared/noop/authorized/running/succeeded/failed/uncertain. Audit timestamps use epoch milliseconds, distinct from existing HTTP ISO timestamps. Reconciliation remains separate from original outcome. No credential field belongs to any shared DTO.

M19 must persist the exact request/digest/target and its policy/approval snapshot, fail closed on invalid or stale decisions, and present unknown replies/uncertainty honestly. M20 must arrange OS-authenticated trusted-artifact setup and await signed hello; launching the backend alone does neither. No change to M16 lifecycle or existing workspace approval semantics.

## M17 sandbox contracts

- ToolService remains compatible through optional trusted `configureSandbox({home,protectedPaths,projects})` and `resetSandbox(root):Promise<void>`. These are backend lifecycle interfaces, never model actions or browser-supplied policy. `createApp` supplies effective M16 configuration and live registered-project paths.
- `removeScope<T>` may now return `Promise<T>`. It synchronously rejects active work/dirty buffers/background jobs, gates the scope while awaiting teardown, rechecks leases, then invokes the callback synchronously. Disk removal also rechecks the current unexpired token and canonical identity after draining, before marking removal started. Failed teardown retains sessions, quarantines the scope, prevents reset/deletion/new work and makes backend shutdown reject so profile ownership is retained.
- POST `/api/projects/:id/sandbox/reset`, strict `{}` -> `{ok:true}` only after teardown and private-storage removal. Existing local-origin, JSON, registered-project, runtime-exclusion, dirty-buffer, pending/background and removal-error gates apply. Unsupported trusted service returns 503. No model action, source/dependency deletion or approval change. `node_modules` and `.venv` remain in the project; only private home/cache/temp/policy storage is cleared.
- Command failures include actionable `SANDBOX_UNAVAILABLE`, `SANDBOX_UNSAFE_PROJECT`, `SANDBOX_UNSAFE_STORAGE` or `SANDBOX_CLEANUP_FAILED` ToolResult codes. Windows, root execution, missing prerequisites and disabled namespaces never fall back to host execution. Existing PTY cwd/session/queue/cancellation, output/JUnit and stale-file semantics remain. A changed protected layout discards shell state and requires an explicit resubmission; no automatic replay.
- Fixed Git reads now require Linux sandbox support. Arbitrary shell `.git` access is masked; shell commit/branch operations on the imported repository are intentionally unavailable. New empty repositories are initialized through a fixed file layout without a host subprocess. Network policy and concurrent-host-edit limits are in `architecture.md`.

Types in shared/types.ts are the integration boundary. All JSON API failures return `{ error: string }`. IDs are opaque strings. Times are ISO strings. Project paths are backend filesystem paths (Linux paths when running in WSL). API routes use /api. Vite proxies that prefix in development; production serves the built UI from the same origin.

## HTTP interface (coordinator implements)

- GET /api/settings -> PublicSettings (never credentials); approvalMode reflects the persisted future-chat default, falling back to backend APPROVAL_MODE.
- GET /api/preferences -> Preferences { debugMode: boolean, defaultApprovalMode: ApprovalMode }; backend-wide durable preferences, Debug defaults to false.
- PATCH /api/preferences { debugMode?, defaultApprovalMode? } -> Preferences; strict partial update, persists only those preferences. Existing chats, pending proposals and workspace settings remain unchanged.
- POST /api/connection-check {} -> ConnectionReport { ok, completedAt, checks: [{target:'catalog'|'architect'|'coder'|'critic', status:'passed'|'failed'|'skipped', message}] }. Uses the configured provider transport and managed account scheduler for completion probes. Report messages are fixed safe text, without raw replies, catalog contents, URLs, credentials or parser exceptions. A failed check returns HTTP 200 with ok:false; a concurrent check returns 409, shutdown rejects new checks with 503. Requires an empty JSON object and the existing local-origin policy.
- GET /api/models -> { models: string[], catalog: ModelCatalogEntry[] }
- GET /api/provider-settings -> ProviderSettings { models: {architect,coder,critic}, apiKeyConfigured: boolean, lockedFields: string[] }. Returns effective new-chat defaults, never the key. Locked field names are architect/coder/critic/apiKey.
- PATCH /api/provider-settings { models?: {architect?,coder?,critic?}, apiKey?: string } -> ProviderSettings. Strict partial update. Omitted apiKey stays unchanged; empty string explicitly clears it. Persists backend `.env`; model defaults affect new chats only. Uses the existing local-origin and JSON protections.
- GET /api/projects -> Project[]
- POST /api/projects { name, path?, mode: 'create' | 'import' } -> Project; create without path allocates a new unique folder inside the configured workspace. Import requires a selected absolute directory path.
- GET /api/workspace -> WorkspaceSettings { workspaceRoot, defaultWorkspaceRoot }; default is ~/React Harness Projects or HARNESS_WORKSPACE_ROOT.

## Provider module (M1)

### Provider settings and saved chat models (M14)

`RoleModels` is `Record<AgentRole,string>`. `Chat.models?: RoleModels` is optional for trusted construction; production initializes defaults before creating chats, and every new chat receives a cloned map. Old profiles are rejected, not backfilled into the native protocol. `Store.initializeModels` backfills missing records only; `chatModels` fails closed on an uninitialized record, and `setModelDefaults` changes only future creation. No secret is stored in chat records or SQLite. All runtime role calls, resume paths and compaction calls/cache keys use saved assignments. No SQLite table/schema change is needed because chat metadata is persisted JSON.

PATCH validates all fields before changing defaults/key. Each model is 1–1024 characters with no surrounding whitespace, newline, control characters or Unicode line separators. API keys are at most 1024 characters with the same single-line/control restriction; empty explicitly clears, whitespace-only is rejected. Values are quoted for dotenv and parsed back for exact equality; combinations that cannot be represented safely with the supported quote styles reject explicitly. Unrelated declarations/comments/line endings are preserved; replaced managed declarations (including duplicates/multiline values) are removed and authoritative values appended. Unsupported declaration syntax rejects instead of retaining ambiguous old managed values. Files must be UTF-8, at most 1 MiB, and regular with one link.

The original process environment takes precedence over `.env`. A model/key field present there, even empty, is reported locked and any attempt to write it rejects with 409; a mixed patch is not partially applied. Production bootstrap uses the selected stable home's `profile/config/.env`; an ambient cwd `.env` never overrides an initialized profile. `DOTENV_PATH`, `DOTENV_ENCODING`, `DOTENV_OVERRIDE`, `DOTENV_FAST` and corresponding `DOTENV_CONFIG_*` options are unsupported and reject startup explicitly. Quiet/debug options do not enable logging. Preloading dotenv through an external launcher makes its injected variables process overrides and therefore locks those fields. Other configuration still requires a restart. API callers cannot select the configuration path.

`.env` writes are synchronous and atomic within this backend. Backfill commits before file replacement. Validation, stale-file, linked-file and replacement failures leave live configuration/future defaults unchanged (trusted initialization may already have committed). Replacement publishes new live settings synchronously before any await. If immediate post-replacement identity/content verification fails, the API returns 409 with an explicit **saved and active; restart after checking `.env`** message, and all later saves are blocked until restart. It never silently adopts unseen external edits. An ordinary external file edit also requires restart before another UI save. No automatic write replay is performed.

`ReloadingProvider` takes a function returning `StarkProviderOptions`, snapshots it per invocation, and uses a separate immutable provider for that request/retries. Keys remain shared backend configuration: queued calls use the key when dispatched; already-dispatched calls finish with their previous captured key. Clear blocks subsequent requests until configured again. Provider errors discard raw upstream bodies/errors, including delayed failures after rotation, without keeping a permanent historical-key collection. Diagnostics keeps the models captured at check start but credentials follow the same per-request dispatch rule; its scheduler is not replaced on settings saves. Saving from Settings clears superseded diagnostic results without restarting active chat work. Rotation does not change the native protocol or approval policies.

Embedding `createApp` requires optional trusted `providerSettingsFile` to enable writes; production supplies it from `loadBackendConfig`. Without it the provider settings fields are read-only. The service assumes one backend and a trusted directory; external filesystem races and Windows ACL limitations are described in architecture.md.

### Native provider, registry and diagnostics (M22)

`ModelMessage` is a discriminated system/user/assistant/tool union. Assistant messages have string `content` (empty for tool-only replies) and optional `tool_calls: NativeToolCall[]`; tool messages require `tool_call_id`. A native call is `{id,type:'function',function:{name,arguments:string}}`. `CompletionResult` retains text/usage and adds toolCalls and sanitized requestId; native completion must finish with `tool_calls`, ordinary text with `stop`. `ModelProvider.complete` accepts generated `tools`, `toolChoice`, and internal per-invocation `streaming`. Summary calls use ordinary text. No response-format requirement, Responses endpoint, prose extraction or legacy adapter exists.

The provider bounds the body to 4 MiB, each SSE frame to 1 MiB, calls to 16, IDs to 200 ASCII characters, names to 64 and arguments to 1,100,000 UTF-8 bytes. It assembles interleaved fragments by index, binds stable unique IDs, requires completed arguments and normal finish plus `[DONE]`, and rejects refusal, truncation, conflicts and malformed history. Argument JSON rejects duplicate decoded keys at every depth. Registry schemas impose additional field/array bounds, with documented UTF-8 bounds. Invalid complete batches receive correlated errors and execute no calls. Terminal controls must be last; multiple terminal calls cannot execute.

`server/tool-registry.ts` owns arguments, published JSON schemas, result schema, descriptions, roles/modes/effects/risks, inspection and handler routing. WorkspaceTools reuses the same arguments. Runtime enforces roles and mode again at execution and preserves scope, version, lease, sandbox, approval and package-policy checks. `submit_completion` concludes a work frame; coder completion is reviewed, critic uses `review_result`, and neither establishes future M24 goal completion. Ordinary architect prose is conversation. Internal prose receives bounded continuation, then an actionable pause after three text-only turns.

Omitted, null and empty tool-call arrays mean zero calls for ordinary nonempty replies finishing with `stop`; a `tool_calls` finish with zero calls rejects. Handler results require a strict boolean `ok`, output bounded to 2,100,000 UTF-8 bytes, and optional finite JSON data bounded to 16,000,000 serialized bytes, 100,000 nodes and depth 64. Cyclic/nonserializable data rejects. Invalid post-effect results retain uncertainty and cannot authorize replay.

Native intake, control transitions/results, preparation, dispatch claims and result delivery use durable state before effects. Private `native:frame`, `native:result`, `native:ids` and context archives preserve original evidence; long model-facing results reference bounded private evidence. Compaction preserves assistant batches/results together and refuses unresolved groups. Tool schemas and serialized native arguments/results count toward context and account budgets. Recovery atomically invalidates obsolete proposals and closes unstarted calls; executing workspace actions and helper operations retain uncertainty and are never replayed. Pending helper decisions follow their existing independent recovery rules. Restart never resumes execution automatically.

Connection checks have a 180-second total bound and separate ordinary, nonstreaming native, and streaming native evidence for each exact configured role ID. Each native probe calls only a harmless in-memory `connection_echo`, returns a matching tool result, then verifies ordinary acknowledgment. No workspace context, shell/file/package handlers, or private transcript is available. Manual IDs can be probed when absent from the catalog; catalog metadata remains untrusted and capabilities unknown until observed in these specific probes. Safe fixed failures, usage accounting, cancellation, concurrency exclusion and noRetry apply. Passing this fixture does not establish task quality or installed-device acceptance.

GET `/api/models` adds `catalog:[{id,metadata,capabilities:{ordinary:'unknown',native:'unknown',streaming:'unknown'}}]` alongside the existing IDs. ConnectionCheck adds `evidence`, `model` and optional sanitized `requestId`. Settings shows each evidence lane separately without adding a protocol/streaming toggle. `PublicSettings.protocol` is `native-tools-v1`; `limitSource:application-budget` and `providerLimits:unknown` distinguish configurable local budgets from provider claims.

The selected profile marker and database `prototype:protocol` must identify `native-tools-v1`. Old populated state is rejected before normal writes; existing data/projects are preserved. New chats snapshot selected models. Candidate defaults are `gemini-3.5-pro` architect/critic and `gemini-3.5-flash-withtools` coder, with no live verification claim. Exact IDs remain configurable; select 3.8 Flash only if exposed by the endpoint.

### Terminal command evidence (M11)

`command` events carry `CommandEvent`: `{commandId,agentId,sessionId,role,action,status,output?,exitCode?,cancelled?,timedOut?,shellReset?,truncated?,message?}`. They cover `run_shell`, `execute_python`, and `run_tests`. `commandId` is the durable pending-action ID. `agentId` identifies the originating frame; `sessionId` is the logical shell-pool key (`frame.shellId ?? frame.id`) within that chat/project, not proof that a particular OS process survived. The existing single coder uses `coder-primary` across delegated frames; shell reset evidence remains explicit. Python actions retain their source rather than presenting an invented shell command.

`running` records dispatch intent, atomically with persisted `executing`. It is the last recorded lifecycle state, not proof that a shell has already started or is still live. `completed` requires observed command exit 0; `failed` requires an observed nonzero exit. `interrupted` requires actual tool cancellation/timeout evidence. A cancellation request alone leaves the command running until a result arrives. Missing exit evidence, thrown execution errors, and shell loss before a command boundary yield `uncertain`; no success is inferred from model prose, tool `ok`, or missing events. A shell-process exit before the boundary is not exposed as a command exit code. A run_tests command can complete with exit 0 while its report is unavailable/invalid: the lifecycle preserves exit 0, includes a separate tool-problem message, and leaves the structured TestReport status unchanged.

Final command evidence is committed with the action's `done` stage. It includes a replacement output snapshot only when actual `ToolResult.data.output` exists, limited to its last 64,000 JavaScript string characters. Diagnostics retain at most 16,000 characters plus the fixed tool-problem prefix. `truncated` indicates either the tool's byte limit or this snapshot limit. Actual shell truncation survives cancellation, timeout, shell exit, and disposal. Output is plain text; frontend strips common console control sequences and escapes markup, with no input or terminal emulation.

New `tool` events retain their existing fields and add exact commandId/sessionId correlation (also present on other new workspace-tool records). New `tool_output` events carry these IDs, retain at most the last 16,000 characters per chunk, and flag omitted text. Runtime stops accepting output callbacks when execute resolves/rejects. The UI deduplicates by event ID, groups only matching command/agent/session IDs within the current chat, and replaces overlapping chunks with a retained final snapshot. Missing snapshots preserve available streamed evidence. Legacy tool events/output without correlation stay unassociated, even if text or agent IDs appear to match. A retained chunk without lifecycle evidence has unknown outcome; a retained completion with exit evidence remains useful even if its start was omitted.

`ChatDetail.events` remains the latest 1,000 events; additive optional `eventsTruncated` is supplied by the current backend when older events were omitted. Global event-ID gaps are not used to infer omission. The UI indicates omitted history, missing starts/results and bounded output. This is a recent-history view, not full archive pagination; retained event rows remain in SQLite. Reconnect uses existing SSE Last-Event-ID replay and durable HTTP refetch; frontend subscribes to `command` as well as existing events. Disconnection identifies displayed outcomes as last recorded rather than live state.

Startup recovery emits `uncertain` for every persisted executing command, including paused/interrupted chats, before any resume. An additive internal `PendingAction.commandOutcomeRecorded` marker is committed with that event. Repeated recover/resume does not duplicate it, does not replay the command, and preserves executing/done recovery evidence. Previously completed actions are not retroactively assigned success; legacy unmatched output is never attached to a newly recovered identity. No SQLite schema, dependency, approval, model protocol, editor lease, or shell-environment changes.

### Error identity and presentation (M12)

New runtime `error` and completed/rejected `tool` events add optional `messageId`, identifying the exact durable transcript message for that evidence. Caught recommendation/policy/inspection errors now have a failed tool message at their original transcript position. Deduplication uses that identity and replayed event IDs only, never matching text. Legacy events without a link remain visible (potentially alongside an older duplicate message); missing linked messages do not hide errors. Event-only failures are placed using retained message event order, with timestamps as fallback when the bounded event history omits message events. Old event-only failures outside the existing 1,000-event window remain an existing history limit; no migration or fabricated attribution is performed.

New tool message metadata may include `commandId`, `commandStatus` and `exitCode`, copied from the existing observed command lifecycle rules, or `rejected:true` for recommendation/policy/inspection rejection. `commandId` is the pending-action ID and can also identify a non-command workspace action, matching existing tool events. Exit 0 with `ok:false` is presented as a command success with a separate tool/report problem; failed reports, unknown outcomes, cancellation and timeout evidence are preserved. Legacy messages use a neutral tool-problem label without inferring command exit. Uncertain/interrupted/failed command messages remain visible with Debug off even if an inconsistent tool result says `ok:true`.

The composer shows current connection/request problems only; a successful durable refresh clears connection errors and a local action error can be dismissed or cleared by a subsequent action. Dismissal does not change approvals, run status or durable evidence. Historical errors stay in the transcript. A stopped-run notice follows current chat status.

M22 removes the earlier advisor envelope, fence recovery and formatting retries. Only complete native calls can request effects. Tool and command outcomes remain durable evidence; checkpoint verdicts cannot rewrite failures. Errors never include raw rejected provider payloads.

No new endpoint, shared type, SQLite schema, dependency, approval policy or shell environment change.

Restart or eviction requires a fresh preview. - POST `/api/projects/:id/change/:changeId/undo` with strictly `{expectedHash: SHA256, previewToken: UUID}` -> `{ok:true}`. No client replacement content is accepted. Requires confirmed state, matching token/hash, no active runtime promise and no running/awaiting-approval chat anywhere in the project. Explicitly pause work first; the endpoint never interrupts it. Missing/wrong-project records return 404, stale tokens/versions and busy/dirty conditions return 409. Existing local-origin/JSON restrictions apply.

Additive SQLite `file_changes` stores unique action ID, project ID, status, bounded summary metadata and full before/after snapshots (each within the file-tool 2 MB limit). `recording` plus execution intent are persisted together before tool execution. A matching successful path/hash result promotes to `confirmed` together with durable action `done`; failures known to precede target mutation are `rejected`, other outcomes `unknown`. Old executing/done actions have no fabricated history. Restart maps `recording`/`undoing` to `unknown` and never replays them. History is not automatically pruned.

Optional trusted `ToolService.restore(root,path,before,expectedHash,beforeMutation)` restores previous content or removes one new file. It is never a model tool. It shares ordinary save locks and performs path, regular-file/link, hash and editor-lease checks. The synchronous callback runs after final safe preconditions and before rename/unlink; it atomically claims `confirmed -> undoing`. Rejected preconditions leave both record and token reusable. Failure after the claim is uncertain and non-replayable even if a mutation cannot be proven; success becomes `undone`. Duplicate requests/tokens cannot claim twice. The runtime holds a project guard across the whole operation and releases it in `finally`; submit/resume/approval and automatic launches respect this guard. Running promises remain authoritative during cancellation.

Executing/done recovery evidence is preserved. M9 guidance is revalidated after the new pre-execution snapshot read. Root AGENTS.md undo also triggers ordinary guidance freshness checks on resume.

Exact content checks cannot detect changes reverted to identical bytes or exclude external filesystem races after the final check; the guard and leases coordinate one backend instance, not arbitrary external writers. Preview UI preserves the mounted editor and exposes omitted history or unavailable diffs explicitly.

The private home `backend.json` contains `{version:1,address,key,identity}` after startup. Do not expose this file or key to the renderer/model/shell environment. Today's same-user unsandboxed commands can still read disk; M17 supplies that missing boundary.

- POST `/api/backend/readiness` and POST `/api/backend/shutdown` accept strict `BackendProofRequest {instanceId,nonce,expiresAt,mac}`. Nonce is 32 random bytes as lowercase hex; expiresAt is integer Unix milliseconds, not expired and no more than 30 seconds ahead. Recommended requests expire in 15 seconds.
- Request MAC is HMAC-SHA256 with the launch key string (UTF-8), lowercase hex output, over UTF-8 `JSON.stringify(['abyssus-backend-v1',action,instanceId,nonce,expiresAt])`; action is exactly `readiness` or `shutdown` matching the route. No key goes in the URL, body, response, public settings or logs. Constant-time MAC comparison is used. Wrong key/instance/action, expired requests and replayed nonces return 403; malformed inputs return 400, valid-auth nonce-cap exhaustion returns 429 (4,096 outstanding nonces, expired entries removed).
- Successful response is `BackendProof {action,identity,nonce,mac}`. Response MAC covers `JSON.stringify(['abyssus-backend-v1','proof',action,nonce,expiresAt,identity])` in the returned property order. The launcher checks instance/profile/protocol, expiry, nonce, action, MAC and `state==='ready'` before attaching. Exported `signBackendRequest`/`verifyBackendProof` implement serialization and signature validation; the caller still checks expected profile and readiness state. `/api/health` remains a simple unauthenticated health check and cannot substitute for this proof.
- Shutdown immediately enters stopping and rejects ordinary new requests with 503. Its signed stopping response acknowledges acceptance, not completed shutdown. After that response finishes, backend close drains requests/SSE/runtime/tools/store and releases ownership. Failed/hanging close remains failed/stopping and retains locks; an owning launcher can observe failure/timeout and explicitly decide whether to terminate its own exact process. Never kill a process based only on its port or a stale PID/descriptor.

Existing loopback Host/Origin and JSON rules apply to lifecycle routes. Invalid-origin requests cannot bypass them even with a valid MAC. The endpoint does not add native tools, model execution authority, new approval modes or automatic action replay. No provider secret appears in the new shared DTOs. M20 must keep launcher credentials in its trusted process and translate initialization/migration flags into explicit setup choices.
