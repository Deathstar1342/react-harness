# Integration contract

Types in shared/types.ts are the integration boundary. All JSON API failures return `{ error: string }`. IDs are opaque strings. Times are ISO strings. Project paths are backend filesystem paths (Linux paths when running in WSL). API routes use /api. Vite proxies that prefix in development; production serves the built UI from the same origin.

## HTTP interface (coordinator implements)

- GET /api/settings -> PublicSettings (never credentials); approvalMode reflects the persisted future-chat default, falling back to backend APPROVAL_MODE.
- GET /api/preferences -> Preferences { debugMode: boolean, defaultApprovalMode: ApprovalMode }; backend-wide durable preferences, Debug defaults to false.
- PATCH /api/preferences { debugMode?, defaultApprovalMode? } -> Preferences; strict partial update, persists only those preferences. Existing chats, pending proposals and workspace settings remain unchanged.
- POST /api/connection-check {} -> ConnectionReport { ok, completedAt, checks: [{target:'catalog'|'architect'|'coder'|'critic', status:'passed'|'failed'|'skipped', message}] }. Uses the configured provider transport and managed account scheduler for completion probes. Report messages are fixed safe text, without raw replies, catalog contents, URLs, credentials or parser exceptions. A failed check returns HTTP 200 with ok:false; a concurrent check returns 409, shutdown rejects new checks with 503. Requires an empty JSON object and the existing local-origin policy.
- GET /api/models -> { models: string[] }
- GET /api/provider-settings -> ProviderSettings { models: {architect,coder,critic}, apiKeyConfigured: boolean, lockedFields: string[] }. Returns effective new-chat defaults, never the key. Locked field names are architect/coder/critic/apiKey.
- PATCH /api/provider-settings { models?: {architect?,coder?,critic?}, apiKey?: string } -> ProviderSettings. Strict partial update. Omitted apiKey stays unchanged; empty string explicitly clears it. Persists backend `.env`; model defaults affect new chats only. Uses the existing local-origin and JSON protections.
- GET /api/projects -> Project[]
- POST /api/projects { name, path?, mode: 'create' | 'import' } -> Project; create without path allocates a new unique folder inside the configured workspace. Import requires a selected absolute directory path.
- GET /api/workspace -> WorkspaceSettings { workspaceRoot, defaultWorkspaceRoot }; default is ~/React Harness Projects or HARNESS_WORKSPACE_ROOT.
- PATCH /api/workspace { workspaceRoot } -> WorkspaceSettings; persist the absolute default folder for future projects without moving existing projects.
- GET /api/directories?path= -> DirectoryListing { path, parentPath, entries:[{name,path}], roots:[{name,path}], truncated }; browse backend directories for import or workspace selection. Default path is the backend user's home. Entries are folders, sorted by name, excluding hidden folders; root shortcuts include Home, Workspace, and available drive/filesystem roots.
- GET /api/projects/:id/chats -> Chat[]
- POST /api/projects/:id/chats { title?, approvalMode? } -> Chat; omitted approvalMode uses the persisted future-chat default at creation time. The server snapshots current role model defaults into additive `Chat.models`.
- GET /api/chats/:id -> ChatDetail
- PATCH /api/chats/:id { title?, approvalMode? } -> Chat; a different approvalMode returns 409 while running, awaiting approval, or holding any pending proposal. Pause/resolve work first. A policy change never starts/resumes a run, decides a proposal, changes another chat, or changes the future-chat default.
- POST /api/chats/:id/messages { content } -> { accepted: true }; running chat messages are steering. /plan plans without tool mutations; /btw steers.
- POST /api/chats/:id/control { action: 'pause' | 'resume' | 'interrupt' } -> { ok: true }
- POST /api/approvals/:id { decision: 'approve' | 'deny' } -> { ok: true }
- GET /api/chats/:id/events?after=0 -> SSE with id, event=type, data=JSON. Events include message, status, delta, plan, approval, tool, tool_output, tests, file_changed, steering, error. Reconnect by Last-Event-ID. UI may refetch chat detail on durable events.
- GET /api/projects/:id/files?path= -> FileEntry[] (one directory)
- GET /api/projects/:id/file?path= -> FileSnapshot
- PUT /api/projects/:id/file { path, content, baseHash, owner } -> FileSnapshot; conflict HTTP 409
- POST /api/projects/:id/editor { path, owner, dirty } -> { ok: true }; heartbeat renews dirty lease while open, explicit false releases

## Provider module (M1)

### Provider settings and saved chat models (M14)

`RoleModels` is `Record<AgentRole,string>`. `Chat.models?: RoleModels` is optional for historical wire/source compatibility; production startup backfills every missing map transactionally before recovery or serving requests, and every new chat receives a cloned map. `Store.initializeModels` backfills missing records only; `chatModels` fails closed on an uninitialized record, and `setModelDefaults` changes only future creation. No secret is stored in chat records or SQLite. All runtime role calls, resume paths and compaction calls/cache keys use saved assignments. No SQLite table/schema change is needed because chat metadata is persisted JSON.

PATCH validates all fields before changing defaults/key. Each model is 1–1024 characters with no surrounding whitespace, newline, control characters or Unicode line separators. API keys are at most 1024 characters with the same single-line/control restriction; empty explicitly clears, whitespace-only is rejected. Values are quoted for dotenv and parsed back for exact equality; combinations that cannot be represented safely with the supported quote styles reject explicitly. Unrelated declarations/comments/line endings are preserved; replaced managed declarations (including duplicates/multiline values) are removed and authoritative values appended. Unsupported declaration syntax rejects instead of retaining ambiguous old managed values. Files must be UTF-8, at most 1 MiB, and regular with one link.

The original process environment takes precedence over `.env`. A model/key field present there, even empty, is reported locked and any attempt to write it rejects with 409; a mixed patch is not partially applied. Production bootstrap uses the selected stable home's `profile/config/.env`; an ambient cwd `.env` never overrides an initialized profile. `DOTENV_PATH`, `DOTENV_ENCODING`, `DOTENV_OVERRIDE`, `DOTENV_FAST` and corresponding `DOTENV_CONFIG_*` options are unsupported and reject startup explicitly. Quiet/debug options do not enable logging. Preloading dotenv through an external launcher makes its injected variables process overrides and therefore locks those fields. Other configuration still requires a restart. API callers cannot select the configuration path.

`.env` writes are synchronous and atomic within this backend. Backfill commits before file replacement. Validation, stale-file, linked-file and replacement failures leave live configuration/future defaults unchanged (a safe legacy backfill may already have committed). Replacement publishes new live settings synchronously before any await. If immediate post-replacement identity/content verification fails, the API returns 409 with an explicit **saved and active; restart after checking `.env`** message, and all later saves are blocked until restart. It never silently adopts unseen external edits. An ordinary external file edit also requires restart before another UI save. No automatic write replay is performed.

`ReloadingProvider` takes a function returning `StarkProviderOptions`, snapshots it per invocation, and uses a separate immutable provider for that request/retries. Keys remain shared backend configuration: queued calls use the key when dispatched; already-dispatched calls finish with their previous captured key. Clear blocks subsequent requests until configured again. Provider errors discard raw upstream bodies/errors, including delayed failures after rotation, without keeping a permanent historical-key collection. Diagnostics keeps the models captured at check start but credentials follow the same per-request dispatch rule; its scheduler is not replaced on settings saves. Saving from Settings clears superseded diagnostic results without restarting active chat work. Model prompts, ordinary Chat Completions, protocol, approvals and stream behavior are unchanged.

Embedding `createApp` requires optional trusted `providerSettingsFile` to enable writes; production supplies it from `loadBackendConfig`. Without it the provider settings fields are read-only. The service assumes one backend and a trusted directory; external filesystem races and Windows ACL limitations are described in architecture.md.

### Connection diagnostics (M8)

One diagnostic can run per backend. Its 25-second total deadline includes catalog retrieval, scheduler queue waits and all three serial role probes; the browser uses a 30-second upper bound and exposes Cancel check. Disconnect, Settings close and backend shutdown cancel outstanding work. Unattempted roles are reported as skipped (shown as "not checked"). No automatic retries are added; the production provider already has internal retries disabled.

The catalog must contain each exact configured model ID. Available roles each receive a small ordinary text request for the version-1 final envelope with the fixed message `Connection OK`, capped at min(1024, configured max output tokens). Diagnostics uses the configured streaming behavior; it does not send native tools or response_format. Normal scheduler estimates/reported usage and conservative uncertain charges apply, including failed/aborted probes. Catalog access is one bounded GET, not a token-bearing completion reservation. Small context/account budgets may reject the test before transport.

Only complete, strict final replies with the expected message pass; actions, refusals, wrong envelopes, malformed/oversized replies and incomplete finishes fail. Completed text is limited to 2048 characters for diagnostic parsing; existing provider byte/stream bounds apply before it. There is no tool/runtime execution path and no project/chat context or durable model transcript for a probe. Budget, authentication, throttling, refusal, timeout, truncation/output limit and invalid-reply failures have sanitized explanations. Passing diagnostics verifies this small probe, not general task quality or full live-provider acceptance.

server/provider.ts exports StarkProvider implementing ModelProvider. Constructor accepts `{ baseUrl: string, apiKey: string, streaming?: boolean, timeoutMs?: number }`. No server config import. server/protocol.ts exports parseAgentResponse(text): AgentResponse; invalid, partial, unknown actions, or malformed arguments throw descriptive errors. Export protocolInstructions(role) with role-specific JSON output instructions. No tools or response_format in provider requests. Use fetch and AbortSignal. Tests use local fake HTTP servers.

Response envelope: `{ version: 1, type: 'action', message: 'Reading the file.', action: { name: 'read_file', args: { path: 'README.md' } } }`. A final/message envelope has no action. Schemas must be bounded and strict. Tool response data is supplied as ordinary user messages clearly identified as tool results.

Tool action argument contracts:

- list_files: { path?: string }
- read_file: { path: string }
- search: { query: string, path?: string }
- write_file: { path: string, content: string, baseHash: string | null } (null only for new files)
- run_shell: { command: string, timeoutMs?: number }
- execute_python: { code: string, timeoutMs?: number }
- git_status: {}
- git_diff: { path?: string }
- run_tests: { command: string, reportPath?: string, timeoutMs?: number }
- set_plan: { phases: PlanPhase[] }
- delegate: { objective: string, acceptanceCriteria: string[], paths?: string[], planStep?: PlanStepRef }
- review: { focus: string }
- ask_user: { question: string }
- review_result: { verdict: 'pass' | 'changes_requested', findings: string[] }

set_plan/delegate/review/ask_user/review_result are runtime actions, not workspace tool actions. Restrict delegate to architect, avoid recursive delegation. Critic only gets read tools and concludes with review_result; runtime enforces it. Bound repair cycles.

SSE payloads: delta {role, text} signals provisional model activity; text may be empty and is never an executable or completed action; tool_output {agentId, output, commandId?, sessionId?, truncated?}; steering {content, delivered}; file_changed {path, source:'agent'|'editor'|'external'}. Message/status/plan/approval/tests carry their shared type directly. tool carries {agentId,action,result?,commandId?,sessionId?}; error carries {message}. The additive command lifecycle event is described below. Editor owner is a stable per-tab random UUID.

### Terminal command evidence (M11)

`command` events carry `CommandEvent`: `{commandId,agentId,sessionId,role,action,status,output?,exitCode?,cancelled?,timedOut?,shellReset?,truncated?,message?}`. They cover `run_shell`, `execute_python`, and `run_tests`. `commandId` is the durable pending-action ID. `agentId` identifies the originating frame; `sessionId` is the logical shell-pool key (`frame.shellId ?? frame.id`) within that chat/project, not proof that a particular OS process survived. The existing single coder uses `coder-primary` across delegated frames; shell reset evidence remains explicit. Python actions retain their source rather than presenting an invented shell command.

`running` records dispatch intent, atomically with persisted `executing`. It is the last recorded lifecycle state, not proof that a shell has already started or is still live. `completed` requires observed command exit 0; `failed` requires an observed nonzero exit. `interrupted` requires actual tool cancellation/timeout evidence. A cancellation request alone leaves the command running until a result arrives. Missing exit evidence, thrown execution errors, and shell loss before a command boundary yield `uncertain`; no success is inferred from model prose, tool `ok`, or missing events. A shell-process exit before the boundary is not exposed as a command exit code. A run_tests command can complete with exit 0 while its report is unavailable/invalid: the lifecycle preserves exit 0, includes a separate tool-problem message, and leaves the structured TestReport status unchanged.

Final command evidence is committed with the action's `done` stage. It includes a replacement output snapshot only when actual `ToolResult.data.output` exists, limited to its last 64,000 JavaScript string characters. Diagnostics retain at most 16,000 characters plus the fixed tool-problem prefix. `truncated` indicates either the tool's byte limit or this snapshot limit. Actual shell truncation survives cancellation, timeout, shell exit, and disposal. Output is plain text; frontend strips common console control sequences and escapes markup, with no input or terminal emulation.

New `tool` events retain their existing fields and add exact commandId/sessionId correlation (also present on other new workspace-tool records). New `tool_output` events carry these IDs, retain at most the last 16,000 characters per chunk, and flag omitted text. Runtime stops accepting output callbacks when execute resolves/rejects. The UI deduplicates by event ID, groups only matching command/agent/session IDs within the current chat, and replaces overlapping chunks with a retained final snapshot. Missing snapshots preserve available streamed evidence. Legacy tool events/output without correlation stay unassociated, even if text or agent IDs appear to match. A retained chunk without lifecycle evidence has unknown outcome; a retained completion with exit evidence remains useful even if its start was omitted.

`ChatDetail.events` remains the latest 1,000 events; additive optional `eventsTruncated` is supplied by the current backend when older events were omitted. Global event-ID gaps are not used to infer omission. The UI indicates omitted history, missing starts/results and bounded output. This is a recent-history view, not full archive pagination; retained event rows remain in SQLite. Reconnect uses existing SSE Last-Event-ID replay and durable HTTP refetch; frontend subscribes to `command` as well as existing events. Disconnection identifies displayed outcomes as last recorded rather than live state.

Startup recovery emits `uncertain` for every persisted executing command, including paused/interrupted chats, before any resume. An additive internal `PendingAction.commandOutcomeRecorded` marker is committed with that event. Repeated recover/resume does not duplicate it, does not replay the command, and preserves executing/done recovery evidence. Previously completed actions are not retroactively assigned success; legacy unmatched output is never attached to a newly recovered identity. No SQLite schema, dependency, approval, model protocol, editor lease, or shell-environment changes.

### Error identity and presentation (M12)

New runtime `error` and completed/rejected `tool` events add optional `messageId`, identifying the exact durable transcript message for that evidence. Caught recommendation/policy/inspection errors now have a failed tool message at their original transcript position. Deduplication uses that identity and replayed event IDs only, never matching text. Legacy events without a link remain visible (potentially alongside an older duplicate message); missing linked messages do not hide errors. Event-only failures are placed using retained message event order, with timestamps as fallback when the bounded event history omits message events. Old event-only failures outside the existing 1,000-event window remain an existing history limit; no migration or fabricated attribution is performed.

New tool message metadata may include `commandId`, `commandStatus` and `exitCode`, copied from the existing observed command lifecycle rules, or `rejected:true` for recommendation/policy/inspection rejection. `commandId` is the pending-action ID and can also identify a non-command workspace action, matching existing tool events. Exit 0 with `ok:false` is presented as a command success with a separate tool/report problem; failed reports, unknown outcomes, cancellation and timeout evidence are preserved. Legacy messages use a neutral tool-problem label without inferring command exit. Uncertain/interrupted/failed command messages remain visible with Debug off even if an inconsistent tool result says `ok:true`.

The composer shows current connection/request problems only; a successful durable refresh clears connection errors and a local action error can be dismissed or cleared by a subsequent action. Dismissal does not change approvals, run status or durable evidence. Historical errors stay in the transcript. A stopped-run notice follows current chat status.

Model action schemas and advisor wording remain compatible. Format recovery accepts only a complete schema-valid response inside a whole-message triple-backtick fence (optional `json` label, newline-separated delimiters, surrounding whitespace allowed). Prose examples, arrays, extra objects, malformed fences and unfinished outer objects cannot supply executable nested actions. Existing four runtime attempts (initial plus three formatting retries) and one diagnostic formatting retry remain bounded and unchanged. Rejected content and proposed actions are no longer unconditionally logged. Checkpoint verdict text preserves prior execution outcomes and useful findings.

No new endpoint, shared type, SQLite schema, dependency, approval policy or shell environment change.

## Workspace module (M3)

### Root project instructions (M9)

`server/project-instructions.ts` exports `readProjectInstructions(tools, root)`, `ProjectInstructionsError`, `PROJECT_INSTRUCTIONS_LIMIT` (32,000 UTF-8 bytes), and a fixed instruction-priority statement. Reads use `ToolService.read(root, 'AGENTS.md')`, preserving existing confined-path, link/type, encoding and bounded-read checks. The loader additionally checks the returned path, content bound, UTF-8 round trip, NUL exclusion, and SHA-256 consistency. Missing is `{content:'',hash:null}`; empty present files have a SHA-256 hash. All invalid/read-error cases fail closed with fixed actionable text rather than exposing underlying errors or file contents. No nested discovery or truncation.

Internal additive persisted JSON fields: `RunState.instructionsHash?: string|null` and `PendingAction.instructionsHash?: string|null`. `undefined` means not validated (including older stored runs); `null` means observed absent; a string identifies the observed content. A prepared action is stamped with the snapshot that produced its request. Changed guidance or unvalidated legacy prepared actions invalidate pending/approved-but-unexecuted approvals and discard prepared actions across the run's frames. Invalid guidance also clears the run fingerprint so repairing to previous bytes still requires reconsideration. Existing executing/done actions retain their uncertain/recorded results, even when guidance is invalid. Completed approval history is preserved. No SQLite schema, public shared type, tool permission, or dependency change.

Every normal architect/coder/critic request gets a separate fresh guidance prefix; it is not appended to durable frame history or compacted into a summary. The fixed system policy explains that enforced runtime controls/protocol and explicit human requests outrank repository guidance, while the fresh snapshot supersedes conflicting historical project guidance. Project text cannot change parser/permissions/approvals. Context preparation accounts for this prefix and preserves it; original transcripts remain archived by the existing context hooks. Summary-only control calls summarize untrusted historical data and have no action execution path.

Freshness reads occur at loop/request boundaries (also after context preparation and before formatting retries), after provider completions, after tool inspection, during approval decisions, and at final dispatch after approval reinspection. Content changes increment the run generation; in-flight responses from the old generation are discarded before acceptance. Watcher events remain supplemental. POST `/api/approvals/:id` can return 409 when project guidance supersedes the proposal or cannot be safely read; changed awaiting runs refresh their proposals, while invalid files put the run in error until repaired and explicitly resumed. Paused tasks remain paused until resumed.

There is no atomic lock against external editors: changes after the final filesystem read or changes reverted between reads cannot be guaranteed detectable before dispatch. Running tool actions retain their outcomes and are not rolled back. Prompt hierarchy is model guidance, not proof of semantic compliance; runtime authorization and tool safety checks remain independent.

server/tools/index.ts exports WorkspaceTools implementing ToolService; constructor may accept optional configuration but must support no args. Dirty leases expire if the browser disappears and are renewed by editor heartbeats. Save from an owner can commit its own dirty buffer; agent writes cannot bypass another owner's lease. All writes compare content hashes, revalidate paths and prevent symlink/path traversal and .git/.env credential access by model tools. Read-only Git operations preserve existing repos. For shell actions, label effect execute and risk elevated unless genuinely enforced otherwise. Do not pretend cwd is a sandbox. Persistent PTY per chat/agent; only sanitized child environment. Optional node-pty dependency, return an actionable explicit unavailable error if unsupported; do not fake shell persistence. Parse JUnit reports into TestReport and return as ToolResult.data.testReport. Bound file/output sizes, timeouts, and command queues.

## Changes review and undo (M10)

- GET `/api/projects/:id/changes` -> `ProjectChanges`: `git` status entries (`status`, `path`, optional `originalPath`), optional `gitError`, `history` summaries, `historyTruncated`. History is latest 100 entries, without content snapshots; all write attempts are labelled by status. Git status includes all untracked file paths rather than collapsed directories, bounded by the existing 1 MB Git output limit. Errors are explicit; incomplete Git status is not returned as complete.
- GET `/api/projects/:id/diff?path=...` -> `{diff}`: current staged/unstaged Git diff, or an untracked text-file diff against absence. Renames include both original and destination paths. Literal Git pathspecs and protected path/link checks apply. A stale/nonlisted path returns 409; unavailable/oversized diff returns an error. No Git index mutations.
- GET `/api/projects/:id/change/:changeId` -> `ChangePreview`: change summary, recorded `diff`, reverse `undoDiff`, current `expectedHash`, optional `previewToken` or blocking `reason`. Tokens are opaque server-issued values bound to project, change and exact current snapshot, expire after five minutes, and are held only in memory (maximum 200). Restart or eviction requires a fresh preview. Recorded snapshot differences require total input/output <=200,000 UTF-8 bytes, with a one-second diff computation budget; oversized/unsupported previews have no token. A token does not promise runtime/lease availability at execution time.
- POST `/api/projects/:id/change/:changeId/undo` with strictly `{expectedHash: SHA256, previewToken: UUID}` -> `{ok:true}`. No client replacement content is accepted. Requires confirmed state, matching token/hash, no active runtime promise and no running/awaiting-approval chat anywhere in the project. Explicitly pause work first; the endpoint never interrupts it. Missing/wrong-project records return 404, stale tokens/versions and busy/dirty conditions return 409. Existing local-origin/JSON restrictions apply.

Additive SQLite `file_changes` stores unique action ID, project ID, status, bounded summary metadata and full before/after snapshots (each within the file-tool 2 MB limit). `recording` plus execution intent are persisted together before tool execution. A matching successful path/hash result promotes to `confirmed` together with durable action `done`; failures known to precede target mutation are `rejected`, other outcomes `unknown`. Old executing/done actions have no fabricated history. Restart maps `recording`/`undoing` to `unknown` and never replays them. History is not automatically pruned.

Optional trusted `ToolService.restore(root,path,before,expectedHash,beforeMutation)` restores previous content or removes one new file. It is never a model tool. It shares ordinary save locks and performs path, regular-file/link, hash and editor-lease checks. The synchronous callback runs after final safe preconditions and before rename/unlink; it atomically claims `confirmed -> undoing`. Rejected preconditions leave both record and token reusable. Failure after the claim is uncertain and non-replayable even if a mutation cannot be proven; success becomes `undone`. Duplicate requests/tokens cannot claim twice. The runtime holds a project guard across the whole operation and releases it in `finally`; submit/resume/approval and automatic launches respect this guard. Running promises remain authoritative during cancellation.

Successful and uncertain undo outcomes broadcast `file_changed` with `source:'undo'` to all project chats and invalidate prepared approvals through the existing runtime steering path; successful notifications include the restored hash or null for deletion. Executing/done recovery evidence is preserved. M9 guidance is revalidated after the new pre-execution snapshot read. Root AGENTS.md undo also triggers ordinary guidance freshness checks on resume.

Project Git changes have unknown attribution (pre-existing/manual/shell/agent); recorded write history is separate. No Git reset, arbitrary shell undo, whole-task rollback or retroactive snapshots. Exact content checks cannot detect changes reverted to identical bytes or exclude external filesystem races after the final check; the guard and leases coordinate one backend instance, not arbitrary external writers. Preview UI preserves the mounted editor and exposes omitted history or unavailable diffs explicitly.

## Chat and project removal (M13)

- DELETE `/api/chats/:id`, strictly `{}` -> `{ok:true}`. Deletes the chat, its messages/events/approvals/tests, run/plan/context state and its recorded file-change history. Project files and sibling chat records remain. The same conservative project-wide runtime/dirty-lease exclusion as project deletion applies.
- POST `/api/projects/:id/deletion-preview`, strictly `{}` -> `DeletionPreview {canonicalPath,confirmationToken,expiresAt}`. Validates disk eligibility and snapshots the canonical directory/ancestor identity. Maximum 200 in-memory tokens, five-minute expiry. A preview reserves neither runtime availability nor file contents. No side effects on project files.
- DELETE `/api/projects/:id`, strictly `{mode:'app-only'}` or `{mode:'disk',canonicalPath:string,confirmationToken:UUID}` -> `{ok:true}`. Disk mode requires the exact path string returned in the preview (the UI also requires typing it). Unknown extra fields, missing mode, arbitrary paths or replacement content are rejected. Tokens cannot authorize a different registration, replacement directory, or changed ancestry, and are consumed before the first disk mutation. Precondition/dirty rejections do not consume the token. All project tokens are discarded after successful removal.
- `Project.removalError?: string` is additive persisted project JSON, returned by project listing. A durable intent marker precedes disk mutation; failure retains this marker and all app records, and blocks new project work. Startup does not retry. Request a fresh preview to retry remaining files; choose app-only recovery when the folder is missing or disk removal is prohibited. A SQLite failure after disk completion still retains the marker/registration if the transaction cannot commit.
- SSE `chat_removed`: terminal, ephemeral event sent after database deletion, immediately before stream closure, with `{chatId,projectId,projectRemoved:boolean}` and no event ID. It is not appended to deleted history. Clients close the EventSource, cancel refresh/debounce/polling and discard late responses. A missed event is handled by an authoritative GET chat 404. Network failures and other HTTP statuses remain retryable under the existing reconnect behavior.

Existing loopback/origin/JSON protections apply. Missing records return 404; unsafe paths, stale/expired confirmations, active work, pending requests or dirty leases return 409 (filesystem lookup/permission errors retain existing error handling). Removal rejects running/stopping runtime promises, in-flight approval/control work, pending approvals, uncertain executing frames, undo guards, active tool operations, editor leases, queued shell work and known live background jobs. New runtime launches respect the project guard. API request accounting includes manual saves, lease updates, chat creation, imports and workspace preference changes. Disk mode additionally refuses links/junctions/special entries, nested filesystem mounts, filesystem/home/workspace roots or ancestors, application/config/database trees and overlapping registrations. App-only mode does not apply these disk-path exclusions and never deletes project files.

Optional trusted `ToolService.removeScope<T>(root,chatId|undefined,mutation:()=>T):T` fails closed if unavailable. Its implementation requires no in-flight operations or dirty leases, checks scoped shell queues/background jobs, closes only the selected idle chat/project PTYs, then executes the synchronous lifecycle callback. `Runtime.exclusiveRemoval` holds the project guard and additionally checks pending operation lifetimes. `Store.deleteChat`/`deleteProject` atomically remove dependent app records; `Runtime.forgetChats` removes cached frames. These are trusted lifecycle interfaces, never model-facing tools. `Changes.forget(projectId)` drops bounded preview cache entries. Existing model prompts, action protocol, approval policy, and M12 outcomes are unchanged.

One backend instance is assumed. Native pathname APIs do not provide an atomic lock against external rename/link substitution; the implementation repeatedly revalidates identity but does not claim external filesystem confinement. Preflight is bounded to 100,000 entries and depth 128. Synchronous mutation prevents in-process lease races but may delay requests for large/slow trees. No automatic rollback, recycle bin, or automatic deletion replay.

## Durable planning and associated progress (M15)

- Additive `Chat.mode?: 'plan'|'execute'` and `modeVersion?: number` are optional in the shared type for old snapshots but present in current server responses. New chats start `execute`, epoch 0; startup backfills legacy mode from saved `RunState.planOnly`. Ordinary chat PATCH still rejects mode fields.
- POST `/api/chats/:id/start-building`, strictly `{planId:UUID, planVersion:positiveInteger, modeVersion:nonnegativeInteger}` -> HTTP 202 `{accepted:true}`. Requires configured provider, current planning mode, matching plan/revision/epoch and at least one step. Missing/stale state or an active control decision/executing operation returns 409; malformed input returns 400, missing chat 404, unconfigured provider 503. Existing local-origin and JSON restrictions apply.
- The accepted transition is saved under `build:<chatId>` with mode incremented once, a durable user `Start building` message and a new/steered run in one transaction. The run is prepared as a separate draft; cached mode/generation/steering and loop launch are published only after commit, so rollback cannot grant a live request speculative execution permission. Repeating that exact receipt while its resulting mode epoch is current is a no-op. An older receipt after `/plan` is rejected even if the plan is unchanged. A retry never resumes paused work or replays commands. Different structural revision after an accepted receipt does not cause that receipt to execute again.
- POST messages recognizes only entire trimmed `go ahead` / `start building` (case-insensitive, optional one `.` or `!`) as permission to leave planning. A nonempty current plan is required. Prefix `/plan` followed by whitespace/end enters planning. Text in model/tool messages, quoted examples, `/btw go ahead`, conditions and other prose have no transition authority. Normal existing execution-enabled chats remain compatible.
- Additive `Plan.id?: UUID`, `version?: positiveInteger`; empty legacy plans may lack them until saved. Server `revisePlan` owns these fields. Ordered IDs/titles determine structural equality; model status-only re-emission is a no-op. Structural edits increment revision and reset progress, preserving old events. `set_plan` argument shape is unchanged and never imports model `done`/`in_progress` as observed progress.
- Optional strict `delegate.args.planStep: {planId:string,planVersion:positiveInteger,phaseId:string,stepId:string}` must resolve exactly in the current chat. Omission remains supported and creates unassociated work with no inferred completion. Invalid references produce the normal rejected recommendation evidence before coder dispatch. No plan association is guessed from titles, paths or objective text.
- Persisted internal `Frame.planStep`, `reviewDelegationId`, `evidenceEventIds` bind work and its completion critic. Evidence IDs retain the last 100 tool results per frame. Completion requires matching delegation, coder final, structured critic pass, current execution mode, current plan/revision/step owner and some observed coder/reviewer tool evidence. A successful tool result alone does not complete a step. Failed critic repair cycles remain blocked. Legacy phase reviewers retain the current plan and cannot overwrite it.
- Additive `PlanStep.evidence?: {eventId,delegationId,outcome,summary,sourceEventId?}` stores the latest durable summary. SSE `plan_progress` carries `{planId,planVersion,phaseId,stepId,delegationId,status,outcome,summary,sourceEventId?}`. Existing `plan` events also publish the new snapshot. Revision stays stable as progress changes. Source events are ordinary `delegation`, `tool` or `review` records; review events additionally identify delegation, plan association, review kind and bounded tool-event IDs. Progress snapshots/events commit together; delegation creation, coder-final/completion-critic creation and completed review consumption commit with their corresponding frame state. These bounded transitions modify cloned drafts and publish the live root only after successful commit.
- Outcome strings include started, working, failed, awaiting_approval, awaiting_user, reviewing, accepted, changes_requested, missing_evidence, checkpoint_changes_requested, superseded, pause, interrupt, stopped, error, budget and interrupted. Step status remains the compatible pending/in_progress/done/blocked union. Historical failures and uncertain action records are never removed by revision, retry, later pass or migration.

No new SQLite tables, dependencies, approval mode, provider transport or model mode-transition action. Shared DTO fields are additive; the deliberate behavior change is that model-authored completion in `set_plan` no longer creates a phase review capable of fabricating unassociated completion. Use exact associated delegation and completion review instead. The panel is a recent-event view; missing source events are explicitly labelled as archived rather than inferred.


## Backend ownership and launcher lifecycle (M16)

Production `startBackend(options?)` acquires the profile home and canonical config/data locks before Store recovery. Returns `{app, config, profile, lifecycle, address, close}` only after successful listen and private descriptor/binding publication. `close()` is awaited and idempotent. Test/embedding callers using `createApp` directly remain responsible for their own ownership; optional `lifecycle: {identity: BackendLifecycle, close}` adds these routes and a work-admission guard without altering existing browser API DTOs. Startup does not resume uncertain work.

Trusted launcher inputs are process environment only: `HARNESS_HOME` (absolute home), `HARNESS_INIT=1` (explicit new profile), `HARNESS_LEGACY_ROOT` (one selected known source), `HARNESS_MIGRATION_RETRY=1` (fresh retry preserving old staging), `HARNESS_SELECT_DATA=1` (explicit changed effective data target), optional `HARNESS_LAUNCH_KEY` (32 random bytes encoded as 64 lowercase hex characters). One-time controls and launch keys must never be persisted in `.env`. Existing data/workspace/model/provider/prompt overrides preserve precedence. Unix home/config directories are private; Windows privacy uses inherited user ACLs. The backend owns its data in its selected Linux/WSL environment.

The private home `backend.json` contains `{version:1,address,key,identity}` after startup. It is never served through HTTP. `identity` is `BackendIdentity {protocol:'abyssus-backend-v1',instanceId:UUID,profileId:UUID,pid,platform,state}`; states are starting/ready/stopping/stopped/failed. The descriptor's instance and key are launch-specific, and stale files are not liveness evidence. On orderly close it is replaced with a nonsecret stopped record. Do not expose this file or key to the renderer/model/shell environment. Today's same-user unsandboxed commands can still read disk; M17 supplies that missing boundary.

- POST `/api/backend/readiness` and POST `/api/backend/shutdown` accept strict `BackendProofRequest {instanceId,nonce,expiresAt,mac}`. Nonce is 32 random bytes as lowercase hex; expiresAt is integer Unix milliseconds, not expired and no more than 30 seconds ahead. Recommended requests expire in 15 seconds.
- Request MAC is HMAC-SHA256 with the launch key string (UTF-8), lowercase hex output, over UTF-8 `JSON.stringify(['abyssus-backend-v1',action,instanceId,nonce,expiresAt])`; action is exactly `readiness` or `shutdown` matching the route. No key goes in the URL, body, response, public settings or logs. Constant-time MAC comparison is used. Wrong key/instance/action, expired requests and replayed nonces return 403; malformed inputs return 400, valid-auth nonce-cap exhaustion returns 429 (4,096 outstanding nonces, expired entries removed).
- Successful response is `BackendProof {action,identity,nonce,mac}`. Response MAC covers `JSON.stringify(['abyssus-backend-v1','proof',action,nonce,expiresAt,identity])` in the returned property order. The launcher checks instance/profile/protocol, expiry, nonce, action, MAC and `state==='ready'` before attaching. Exported `signBackendRequest`/`verifyBackendProof` implement serialization and signature validation; the caller still checks expected profile and readiness state. `/api/health` remains a simple unauthenticated health check and cannot substitute for this proof.
- Shutdown immediately enters stopping and rejects ordinary new requests with 503. Its signed stopping response acknowledges acceptance, not completed shutdown. After that response finishes, backend close drains requests/SSE/runtime/tools/store and releases ownership. Failed/hanging close remains failed/stopping and retains locks; an owning launcher can observe failure/timeout and explicitly decide whether to terminate its own exact process. Never kill a process based only on its port or a stale PID/descriptor.

Existing loopback Host/Origin and JSON rules apply to lifecycle routes. Invalid-origin requests cannot bypass them even with a valid MAC. The endpoint does not add native tools, model execution authority, new approval modes or automatic action replay. No provider secret appears in the new shared DTOs. M20 must keep launcher credentials in its trusted process and translate initialization/migration flags into explicit setup choices.
