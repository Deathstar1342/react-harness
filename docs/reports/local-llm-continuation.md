# Durable Task Continuation

## Early contract for coordinator review

The user can open Recovery after a longer Coder assignment is paused or interrupted, see what the application retained, and deliberately continue the same eligible assignment with scoped current context. The view distinguishes original decisions, historical observations, current verification and unresolved effects. Resume continues the retained native frame with a fresh provider request through the existing Runtime. Restart restores state for inspection and runs no work.

The baseline is `ec2c0437da5e24f19202b536b6e2f641e622d058` with tree `5f6af94501e41f611b40c49a3e905c9aeb0e4e7a` and lock blob `b495523254847d0770381e4fb52aa26b659633e2`. The delivered [Coder context](local-llm-coder-context.md) provides original Plan task metadata and targeted reads. The delivered [Critic routing](local-llm-critic.md) provides bounded original receipt correlation, fresh source observation and separate verdict/disposition. Exact-main verification of that baseline is prior delivery evidence. This report proposes interfaces and acceptance criteria for review before source changes.

## Original records and display

- The durable source is the existing SQLite `run:<chatId>` and its retained frame, paired with the original Plan reference and existing runtime records. Keep the root and Coder frame IDs, canonical assignment and scope, original Plan ID, version, phase and step, project identity, chat, generation, mode/version, original human message IDs and, where applicable, the current goal and exact queue claim binding. An eligible frame is the current executable Coder with an explicit, valid assignment and exact current Plan step. A nested review, unbound or unscoped legacy frame, popped frame or replaced run cannot become a continuation target. Existing ordinary conversation and review behavior remains available through its current controls.
- Do not write a separate continuation history. Derive one view of the current retained frame from its assignment, bounded evidence IDs, pending and prepared markers, original committed native requests, calls and results, and exact runtime events. Use the existing apply/undo, process, install, preview, checkpoint, queue, goal and approval stores where needed to establish barriers. If a small new field is required to retain an original reference through compaction, version it inside the frame and save it in the same native clone/COMMIT as the source transition. Store IDs and bounded status only. Keep frame storage and its existing replacement/deletion lifecycle. A read, refusal or canceled preparation adds no durable continuation record. Preserve original evidence under its owning lifecycle even if the continuation surface becomes unavailable.
- Show the original objective and acceptance criteria, in-scope Plan check labels, observed progress, and remaining obligations derived from the current exact Plan and original assignment. Link native decisions and approvals to original records, with their recorded pending, granted, denied, expired or stale status. Bind approval to original chat, frame, call, proposal and applicable generation/mode/target. Human approval of one proposal supplies no approval for a new call, a changed proposal, a plan or goal, or another queue admission. The displayed Continue action represents a human control request, with existing controller authentication and actor provenance. Render model notes or compaction summaries as historical narrative only if already exposed through the existing conversation. They cannot supply paths, receipt IDs, decisions, remaining accepted work or completion.
- For prior work, project only stable safe identifiers and allowlisted status from correlated native evidence. Confirmed file mutations link to original file history and their in-scope paths, including both sides of an in-scope rename. A mutation receipt records an applied action at that time. Current bytes/absence, versions and exact-owned Git observations establish what is present now. Preserve the distinctions among working tree, index and HEAD. An automatic packet may report an exact scoped byte match. Index, HEAD, and wider drift remain unverified unless an explicit targeted tool observed them. Git reads follow the existing authorization and sandbox boundary. A reported test pass is historical until its original command/result, substantive report and matching observed scope all support the claim. Failed, missing, reduced, stale, refused and unknown evidence remain distinct. Completion and repair routing stay with the current Coder/Critic/Architect controls.
- Link an existing M34 checkpoint only if its authorized metadata already binds it to this assignment. Its capture and restore protect file versions and have their own admissions and journals. A capture proves neither that an effect settled nor that tests passed. A blocked, unreadable or interrupted restore retains the original barrier even if the rest of the view is unavailable. M37 owns queue order, explicit Start, durable admission and acceptance. The continuation view links the original claim and its stopped state, and cannot admit another task, manufacture acceptance or clear a failure latch. Human control preserves the queue's current stop semantics. An indication that a queue row is next supplies no authority to start it.

## Recovery and bounds

Extend the authenticated, no-store Recovery response with at most one optional `continuation` projection. It identifies the retained Coder and exact Plan step, gives historical coverage and reason codes, and provides an exact-view precondition only when the stored binding can be constructed. Proposed states are `available`, `blocked`, `stale` and `unavailable`. `available` means the persisted candidate can be checked on explicit Resume, with current workspace, ownership and dispatch checks still pending. Old clients can ignore the field. Keep existing Recovery and Inspector links so evidence navigation adds no generic resume, replay or reconcile API.

Use a single read-only SQLite snapshot with equality predicates on indexed original identity and explicit bounded windows for any fallback scan. Proposed ceilings for the added projection are one run envelope at 2 MiB, 24 distinct evidence rows plus an overflow sentinel, 1 MiB per original receipt before field extraction, 64 KiB total projected SQL payload, and 16 KiB serialized public continuation data. Reuse tighter source-specific bounds whenever present. Return exact IDs/status/allowed relative path only, with a 24-reference total, at most eight paths, and at most eight criteria/check labels per category. Use the existing Recovery aggregate budget and coverage accounting. If the added optional section would displace original Recovery evidence, reduce or omit that section and mark its coverage. Store no extra raw source, tool arguments or result bodies, transcripts, absolute paths, private config, credentials or workspace archives.

Check SQLite byte lengths before materializing values in JavaScript. Budget payload and row count before iteration; use bounded header/field projections and exact lookups for receipts. Preserve malformed, oversized and missing row distinctions. Strictly decode authoritative inputs and reject ambiguous duplicate keys or cross-record identity mismatches. Cap traversal/observation with existing checked budgets (500 ms per stage for added evidence and source preparation). A timer alone is insufficient for SQL; bound the query work with exact keys, row limits and compatible indexes. Track truncation even when the cap prevents resolving a receipt. A partial historical display may omit detail. Any incomplete coverage needed to exclude unresolved effects blocks checked Resume. Existing authoritative ledgers must establish that coverage independently of the display window. GET performs no runtime startup or admission, worker or Git probe, approval expiry, goal/queue/checkpoint transition, repair, lease acquisition or reconciliation, and writes no logical rows or events. A projected label supplies no proof of live quiescence.

## Checked Resume and current context

Use the existing chat control route and human Resume gesture. Propose adding an optional bounded opaque precondition to the strict `{action: "resume"}` request on the continuation surface. Bind it to server-derived project/chat, current root/frame/original assignment, generation, exact Plan reference, mode/version and current relevant human, settings, goal and queue-control revision. Include the identity of the retained interruption or the last exact control receipt so that an older view cannot become eligible again after another pause. Where current settings lack a revision, use a server-side fingerprint of the relevant non-secret binding and recheck it at dispatch. The precondition is a stale-view guard. Recompute server-side under the native scope. Repeated or concurrent Resume requests can admit at most one transition for the reviewed interruption. The generic chat Resume route shares the same safety checks when a scoped continuation candidate is present, so stale candidates and unresolved effects cannot bypass them. Ordinary legacy conversations and controls retain existing behavior. A frame rendered stale requires current human steering or a fresh legitimate delegation through existing controls.

1. Serialize against current native control, then verify durable binding against live project registration, exact Plan and assignment identity, generation, scoped human intent, build mode, configured chat-model binding, current guidance and selected skill versions, queue claim and goal revision/status. Recheck after awaited work, at the existing transaction and at actual provider dispatch. Use current AGENTS.md, active role prompt and selected skill guidance. Existing generation changes from steering or guidance invalidate the continuation enrollment, its precondition and any prepared context. Late provider results still use current generation rejection. A scope or revision change forces a fresh review of retained work. Never graft an old frame to a newer revision or silently widen the scope.
2. Use current exact-owner gates for active Runtime, pending human decisions and approvals, dispatched or uncertain native effects, worker/process/preview ownership, installs, project transfer/removal, checkpoint restore journals and mutation reservations, and conflicting editor leases. A live or potentially owned action that has not settled, an unavailable ownership check or a stale human decision leaves the candidate paused, with 409 for changed or blocked controls and the existing fail-closed storage response for unreadable authoritative state. Use existing independently safe cleanup or reconciliation actions with their exact ownership and authorization. Resume performs no adoption, generic cleanup, implicit retry, new approval or dispatch of any retained uncertain action. Proven pre-dispatch abandonment is `not_started` based on committed evidence. Suppress obsolete prepared proposals using existing durable cancellation before any fresh request. A result or journal claiming dispatch without an exact final receipt remains uncertain. A blocked approval still needs its existing human control. A paused or held goal retains its original gates. Resume cannot implicitly start a goal or queue, create a plan approval or admit the next task.
3. In the existing native clone/COMMIT path, record the exact checked control transition and its original binding if the Runtime has no equivalent receipt. Invalidate use of the stale view on commit and publish live state only after success. A failed check or vetoed COMMIT launches no provider or worker and cannot erase retained uncertainty. Treat missing acknowledgements as unproven: read fresh persisted state and show the committed receipt or the still-unresolved claim. Never retry as a new operation or infer no effect from a lost reply. A committed Resume followed by a lost response or restart is observed, with no duplicate launch or automatic restart execution. Continue only through existing scheduler, observer and native tool dispatch protections, keeping all action, approval, version and lease checks for fresh calls.
4. Reuse the Coder task-context reader for the admitted current scope. Start with already-admitted Plan spans and original referenced paths, intersected with the exact assignment. Observe at most eight files, no more than 32 KiB per file and 128 KiB total, with a tighter existing limit taking precedence. No recursive reload, Git diff injection, broad scan or automatic testing. Use existing workspace/version/lease and native storage checks to omit stale, linked, changed, unreadable or dirty editor content. If a source observation merely became stale, report that fact and permit fresh targeted reads under ordinary scope only when the authority and independent effect checks remain intact. If ownership or the trusted workspace itself fails, stay paused. Recheck stamps, current binding and leases after scheduler wait before provider invocation. The packet is transient, inserted after compaction, capped at 2,048 estimated units within configured context and output reserve. Prefer fixed historical status over excerpts for low headroom. If even required current control context cannot fit, stop with the existing context refusal. Preserve original receipts beyond compaction through bounded correlation and make zero additional summary calls for continuation. Reuse current targeted reads and Critic routing for later verification.

Legacy or missing annotations can leave a historical continuation view unavailable and ordinary conversation controls in their original paths. A missing or malformed original receipt cannot be substituted with a newer unrelated success or model claim. For a recognized scoped interrupted assignment, loss of enough evidence to establish the original binding or settle a possible effect leaves it paused. A harmless missing read may be marked unavailable when authoritative dispatch evidence independently excludes an effect. Failure of the continuation projection cannot waive an underlying checkpoint, process, install, approval, goal or queue barrier.

### Behavior

- Recovery projects the retained exact scoped assignment from the current native run, original delegation and Plan, human message IDs, and bounded correlated tool results. The original evidence is historical, including successful file-change and test report entries. The transient Coder request reuses the existing scoped Plan reader for current source. It omits stale or out-of-scope excerpts and introduces no continuation summary request. Fresh targeted tools and the existing Critic determine current evidence and acceptance.
- Existing Resume opens Recovery when a scoped Coder needs a checked control. The exact server-derived precondition covers the observed interruption, original scoped generation and current chat, Plan and model settings. The native commit records the new generation and the original interruption ID first. Stored state and current scoped guidance, skills, worktree identity, ownership and workspace admission are checked again before initial provider dispatch. A second interruption invalidates the old view. An accepted control with a lost response admits at most one initial invocation and is never replayed on startup.
- Malformed, missing, stale, unsettled and damaged continuation requests have no queue intervention or goal budget renewal. Unsettled original effects or an unavailable authoritative binding hold the assignment. Scoped active goal and retained queue claims stay on their existing separate controls. An unrelated conversation or an active completion Critic retains its protected legacy Resume. The real disk-reopen completion Critic regression reaches accepted Plan review without a Coder continuation receipt.
- The checked scope is an explicitly scoped original native Coder delegation with an exact Plan step, a previously observed workspace identity, a retained interruption and complete bounded authority evidence. Earlier scoped records lacking those links remain available for inspection and require current human guidance. Existing confirmed file-change metadata and current scope checks still govern recovery. Missing or ambiguous original effects and exhausted evidence budgets stay paused. A discarded, provably pre-dispatch prepared proposal is retained as `not_started`.
