### Plan fields and revision semantics

Add optional `PlanStep.task` in the existing SQLite JSON. Native callers request it through optional `admission[].task` with `objective` (nonblank, up to 600 UTF-8 bytes) and optional `dependsOn` (up to four unique `{phaseId,stepId}` pairs with existing ID bounds). The pairs must resolve to other steps in the proposal when supplied. They are planning relationships and do not require the referenced step to be accepted before delegation. Preserve absent metadata for legacy steps and callers.

Proposed stored shape follows. All fields except `symbol` and `dependsOn` are present on a v1 task.

```text
task = {
  version: 1,
  admittedAtPlanVersion: positive integer,
  objective: string,
  dependsOn?: Array<{phaseId, stepId}>,
  sources: Array<{
    path, callId, frameId, hash, startLine, lineCount, symbol?
  }>,
  newFiles: Array<{path, callId, frameId}>,
  checks: Array<{method: "test" | "inspection", target, expected}>
}
```

The phase and step own the task. The current Plan revision controls its use. `admittedAtPlanVersion` identifies when these particular references last passed admission. Carry it forward unchanged when retaining a task. `frameId`, `hash` and the observed span come from the runtime's successful original receipts. An entire empty source has `startLine: 1` and `lineCount: 0`. A range means only the lines actually delivered. Existing declaration checks govern optional `symbol`. `excerpt` stays admission-only. Store no excerpt, validation command, absolute path, file identity stamp or workspace body. The checked source refs and new-file refs are the only known path scope in the task. `delegate.paths` remains the assignment scope and intersects these references for automatic loading.

Keep the existing eight unique path, 16 reference, 256 KiB and 750 ms admission caps. An opt-in task stores at most eight combined references and the existing one to four checks (600 UTF-8 bytes per expected result). The serialized task has a 6,144-byte cap. Current path and symbol limits still apply. Empty, conflicting, duplicate or over-budget submitted fields fail strict validation or admission. Legacy admission without a task keeps its existing limits and contract.

Phase and step omission removes the relevant entries under ordinary structural rules. A full `phases: []` clear retains its existing behavior. Omitting `admission[].task` on unchanged steps preserves the saved task even if that step was cited to justify removal or reorder elsewhere. For a step with existing metadata whose definition changes, require a replacement task to re-ground the metadata on the changed definition. A historically unannotated step remains eligible for ordinary admission. Moving a step to another phase still requires fresh admission. An explicit task update can change a revision even when the titles and IDs match. An exact repeat of the saved definition using its original receipt refs is a no-op and does not attest to present freshness. A fresh receipt is an explicit refresh. Caller status, ephemeral timestamps and `excerpt` do not control equality.

Use the same canonical definition comparison for required evidence, no-op checks and Store revisions. Stage derived metadata alongside the prepared admission and publish it only at the existing atomic transition. A declined or superseded revision keeps the old Plan and goal state. A committed metadata revision takes the ordinary plan-revision path, so old delegations and current goal reviews become stale and progress resets as it does on existing structural changes. Retained goals continue to identify their required steps and criteria under existing rules. Metadata supplies no new execution scope, completion predicate, test exemption or review evidence.
