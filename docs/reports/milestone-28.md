# Milestone 28 — container service foundation

Status: contract proposal and implementation in progress. Base: `62af0969ca77f5372857d6904c754f6ec76a5134`; isolated branch `codex/milestone-28`. No main integration, successor, M21 work or release.

## Proposed bounded contract (2026-10-16)

- A pinned Linux x64 Node 24 controller image runs as the invoking non-root UID/GID, with native Linux PTY installed and verified at build time. Its root filesystem is read-only; temporary storage is bounded. No Docker CLI/socket, privileged mode, host network/PID namespace, host home, provider build argument or generic host-command endpoint.
- The trusted Bash source launcher alone calls local Docker/Compose using fixed checked-in assets and allowlisted operations. It rejects remote/TCP/SSH contexts, non-Linux engines and unsupported storage filesystems. It does not install or configure any host prerequisite. `setup.sh --container` and `start.sh --container` select this path before historical source checks; the old default remains until M32.
- Explicit initialization requires a new empty, canonical, private Linux storage directory selected by the operator. Layout: `config/` private native provider file; `state/` native application home (including profile metadata and `profile/state/state.sqlite`); `workspace/` authoritative projects; `runtime/` reconstructible host supervision metadata. State mounts at `/abyssus`, config at `/abyssus/profile/config`, workspace at `/workspace`. This retains the native profile format without migration; the nested SQLite path is intentional. Each mount has the same storage identity. A checkout-local private selection retains root + identity; neither startup nor setup reruns create missing established storage or substitute a new root.
- Host-selected paths and container paths have separate branded TypeScript types. No HTTP DTO accepts a host mount/image/daemon option. Linux local ext4/xfs/btrfs binds are the initial supported storage class. Windows D: remains a distinct host path type, not translated to a Linux string. M31/M32 must validate Windows bind WAL/locking or explicitly offer an engine-managed Linux volume; such volumes physically live in Docker Desktop's configured VM disk (possibly C: unless the operator has already relocated it). M28 never silently selects that alternative or changes global disk settings.
- Initialization creates a native profile and SQLite database before publishing the storage-ready receipt. Startup validates all mount identities and required metadata/database/config before `prepareProfile` can create anything. Existing SQLite exclusive ownership, WAL recovery, runtime recovery and no-replay logic remain authoritative. Concurrent controllers must fail ownership; container recreation must retain project/chat identity and committed WAL contents.
- A fresh controller process uses the existing random transport capability, browser pairing and HMAC lifecycle protocol. Only the container listener may bind `0.0.0.0`; Compose publishes it exclusively on host `127.0.0.1`. Readiness checks make an authenticated request and verify its HMAC/profile identity. Private descriptors stay in controller state; reusable keys never enter logs/arguments/renderer. Pairing is deliberately displayed only to the local operator, as in the source flow.
- M28 explicitly disables all command dispatch (PTY, Python, tests, fixed Git/background execution) and package-helper connections in container mode before any child process is created. File tools retain version/lease/native authorization protections and are confined to `/workspace`. No old Bubblewrap or host-shell fallback.
- M29 broker proposal only: trusted host registers a session, managed project ID, single-use execution claim, bounded command/runtime class and freshness evidence. Host resolves project/image/mount policy itself, returns an owned job identity and durable uncertain status on lost replies. No broker listener or worker executor ships in M28. M29 owns full schema and final freshness/approval callback integration.
- Evidence: portable path/storage/gating/auth regressions plus real disposable Linux image build, native SQLite/PTY check, unauthenticated denial/authenticated readiness, concurrent ownership refusal, crash/WAL recovery, stop/recreate persistence, config secrecy, missing/mismatched mount refusal. No local engine provisioning, Windows engine acceptance, live provider or desktop claims.
