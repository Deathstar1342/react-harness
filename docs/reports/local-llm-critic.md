# Critic Evidence and Repair Routing

## Early contract for coordinator review

Base commit `fbf85a7b469680fe6bcf48e50b3ca47dbfa58ef0`, tree `2cc3e7f88c4f8d8d49caca77f27d16859e1f797b`, feature branch `codex/local-llm-critic`. This report proposes the contract before implementation.

## Existing behavior

Runtime creates separate completion, checkpoint and independent Critic frames. The completion frame inherits the assignment and currently receives a trailing transcript excerpt of up to 100,000 characters. The Critic already has targeted read tools. Assignment evidence tracks ordered tool events, fresh JUnit versus process outcomes, actual test coverage, scope fingerprints, uncertainty and overflow. The completion gate checks the original delegation, process and verification blockers, and explicit goal evidence where applicable. The general evidence-presence check currently counts IDs. Two local repair turns can return the task to the original Coder before it returns to the Architect. Raw `passed` in a review event records the model verdict.

## Review disposition

Keep `review_result.verdict` as `pass | changes_requested` and preserve legacy argument shapes and raw event fields. Add an optional strict `replan` object for completion `changes_requested` with a reason code (`architecture_conflict`, `dependency_blocked`, `invalid_assumption`, or `scope_change`), nonblank explanation of at most 768 UTF-8 bytes, and up to four distinct exact receipt IDs. Require at least one correlated observed receipt supporting the issue. An observation may document a real conflict through a failed operation when that failure is itself correlated and certain; it supplies no successful acceptance evidence. Runtime can check identity, scope, status and availability. The actual interpretation remains the model's assessment. Reject contradictory arguments, invalid reason codes, foreign or unavailable references and a replan request from checkpoint or independent review. Ordinary code fixes use plain `changes_requested`.

Record a bounded Runtime disposition in the existing review event. Proposed values are `accepted`, `local_repair`, `replan`, and `unaccepted` for completion, with a reason and bounded evidence status or limitations. Preserve legacy checkpoint and independent event reading and feedback. Keep the raw model verdict visible alongside the actual disposition. Resolve the native call and commit the event, disposition, progress and any permitted goal acceptance in the existing atomic transition. Pre-veto outcomes emit no durable acceptance or routing.

| Completion judgment and current state | Runtime route |
| --- | --- |
| Pass with exact current binding, sufficient correlated observed evidence and all existing gates open | Record acceptance for the same assignment and exact Plan step when bound. Existing goal and queue transitions keep their own independent checks. |
| Changes requested, or pass with a repairable verification deficiency | Return bounded findings and concrete blockers to the same Coder while under the existing two-repair budget. Preserve the assignment, scope, plan reference, run generation, human constraints and verification history. |
| Valid, supported replan request on an exact current completion | Return the bounded reason, receipt references, scope limitations and applicable blockers to the existing Architect frame. The assignment stays unaccepted. |
| Exhausted budget, unresolved effects, unsafe process state, stale identity or other admission blocker | Follow existing refusal, blocked or Architect handoff as applicable. Preserve uncertainty and avoid presenting budget exhaustion as an architectural finding. |

Replanning conveys information through the existing planning and human approval path. The control transition leaves Plan revision, execution authority, scope, generation and goal/queue acceptance untouched. The original work stays visible. Existing per-run step and goal budgets still apply. Where the same Critic context is retried, reuse availability or historical status rather than repeatedly capturing source. Terminate repair churn through the original per-assignment budget.

## Starting evidence and binding

Use the existing task state for the original assignment, scoped Plan identity and step, and stored human intent. Replace the completion review transcript scaffold with bounded findings from exact evidence records. Capture evidence by indexed receipt ID within the same chat, project, original Coder and current Critic frame. Reuse the existing tool events and native file-change records, their original action IDs and committed outcome; no additional ledger. Project check state from assignment evidence and join only the exact event. Publish distinct statuses for passed observed coverage, failure, stale or missing report, skipped or reduced coverage, unverified scope, effect uncertainty and truncated coverage. Project command exit and report outcome separately. Freeform tool output, Coder claims and model summaries carry no authority.

For current diffs, derive candidates from correlated successful native file-mutation receipts and available explicitly requested scoped Git receipts. Use the existing file-change preimages and current confined observations to form a bounded assignment-relative textual patch in process. Compare recorded hashes across repeated mutations and the current after-image. For create, delete and rename, observe each involved path and require both sides to be in scope before showing a rename patch. For an external edit, mismatched hash, missing link in the receipt chain, unverified workspace, unsupported file, pending operation or exceeded budget, withhold affected hunks or label them partial. Use existing scoped reader and lease guards. An assignment-relative patch has a different base from a Git patch and is labeled accordingly. An explicitly observed Git diff can appear as historical evidence when its index, worktree or source freshness cannot be established. A current Git result that cannot be proved from existing observations gets an explicit unavailable or partial label, including Git-less workspaces. An empty result from the captured subset never means a clean repository. Scope calling is limited to exact explicit file paths or receipt-qualified descendants. Count known out-of-scope modifications without exposing their bodies. Broader drift, unknown worktree baselines and command-created paths without exact receipts stay unverified. Targeted native Git tools remain available for a Critic's explicit inspection. No new automatic command execution or repository walk is needed.

Reuse the Coder source observation confinement and execution checks. Bind capture to the current review kind/frame, originating Coder assignment and Plan step and revision, active run and goal generation, project/workspace identity, mode and instruction state. Recheck after async boundaries and perform a fresh bounded native scope check after the scheduler wait, before provider invocation. The scheduled callback can remove stale packet content and stay within its reservation. No workspace scope is held over a provider or scheduler wait. If an advisory observation fails, retain its safe status where available. Authority failure, cancellation and native observer poison follow the existing refusal path. Capture stays transient and out of durable transcripts, compaction input, events and public API. Retain compact native review outcome facts and receipt references in the existing review/progress records.

Runtime acceptance runs separately from advisory generation. Verify that the review is the exact current completion frame for the same Coder and assignment. For a bound plan or goal, check the live revision and delegation before progress or acceptance. Revalidate receipt presence and admissibility against the originating frame rather than trusting IDs, model text, advisory output or a local status label. Successful compatible exact read evidence for legacy observational tasks remains eligible; failed, empty, stale, foreign or unobserved receipts provide no evidence of successful completion. Missing, excess or malformed evidence fails closed when needed for acceptance. Preserve command/result and coverage blockers, current scoped verification, reservations and process quiescence, approvals and outstanding effects, checkpoint and skill guards, cancellation, native observer veto, COMMIT fences and no replay. Asynchronous scope observation must confirm live binding and reject stale call/assignment/plan/mode/project results. External edits between observations remain a limit of snapshot-based evidence. A new uncertain outcome cannot be cleared by a verdict, retry, packet, or disposition.

## Resource and privacy budget

Initial proposed limits per completion review are 24 projected event rows, 8 candidate files or path pairs, 32 KiB per receipt document or observed text file, 128 KiB aggregate decoded evidence/working text and 16 KiB combined working patch output. Cap emitted context at 2,048 serialized estimator units, including framing, and then clamp to the configured Critic headroom after ordinary preparation. Use a 500 ms total source-advisory observation budget per capture/recheck and at most 50 ms per patch calculation within that budget. Use whole bounded rows/snippets with omission counts. Project SQL fields and guard input size before returning JSON into JavaScript. Query exact existing IDs and keep the authoritative gate within existing receipt limits of 100 IDs per frame, without loading full event bodies for that gate. If a receipt window lost earlier evidence, describe truncation and withhold acceptance where that gap invalidates coverage or origin. Existing verification scope bounds independently apply (128 entries, depth 8, 1,000,000 source bytes and 2 seconds). Source hunks and validation descriptions are untrusted data. Suggest only existing admitted check descriptions, tightly recognized manifest-script names from safe exact observations, or explicit targeted read-only follow-ups. No installation, automatic test, automatic check, host-shell fallback or implicit authorization follows from a hint. Avoid raw shell arguments, output, stdout, secrets, receipt internals and paths outside permitted scope in automatic projections.
