# M33 — Recovery dashboard

## Proposed contract (2026-10-26, before implementation)

- Add authenticated `GET /api/chats/:id/recovery` under the existing transport, Host/Origin and chat ownership checks. It synchronously reads SQLite only: no Runtime control, install history/expiry, helper/worker status, reconciliation, mutation, or execution. No schema migration or dependency.
- A versioned allowlisted DTO contains chat/mode state, observation time, opaque projection revision, latest durable event ID, bounded recovery entries, source event IDs/timestamps and coverage flags. It contains no frame messages, arguments/output, prompts, private evidence ledger, provider/account/endpoint configuration or launcher capability. Goal provenance projects original human message IDs/revision only; plan references retain original evidence event IDs.
- Bounds: latest 500 relevant command/tool events; latest 100 install records; at most 64 owned process records; at most 100 pending/queued calls and 100 plan steps; at most 200 displayed recovery entries. Every omitted source/entry is explicitly truncated; absence is unknown, never not_started/success. Read only bounded SQLite projections rather than bulk-loading transcripts/history.
- Source precedence: owned process/install state provides its own current recorded status (never a fresh host observation); correlated command lifecycle governs command exit outcomes, tool-result evidence governs other tools, durable prepared/queued/recovered not_started results establish non-dispatch only for that exact call. Executing without outcome is running only while the chat is running, otherwise uncertain. Inconsistent correlated evidence is unknown/uncertain and must not manufacture success. Plan pending is unknown, not proof of non-dispatch. Goal completion retains existing runtime acceptance semantics, not new completion logic.
- Entries distinguish completed, failed, not_started, running (last recorded), uncertain, interrupted and unknown. No projection clears uncertainty or interprets model prose. Keep identity links to command/call/frame/process/install/plan and original event IDs where available; missing timestamp/event identity is explicit.
- Action descriptors are navigation only: existing chat controls (Resume/pause), approvals, terminal/process, exact install history and plan/goal panels. Opening a destination never invokes an action. Existing authenticated routes and their current checks remain authority. No new action endpoint or generic uncertainty resolution. Process cancellation remains the existing exact-owned authenticated route.
- UI: quiet header Recovery control, collapsed by default; opening/refresh only GETs; bounded scroll region with source IDs/time, coverage and freshness notices. SSE/chat revisions mark observations stale; async responses from old chats/requests are ignored. Refresh revision is observational, never an authorization token. Navigation focuses existing controls; effects require deliberate existing action clicks and current backend admission.

API tests cover auth/Host/Origin and malformed query/ownership. Existing steering/approval/mode/revision tests plus targeted stale-navigation/browser/Electron checks establish observation versus action separation. Run typecheck, full tests and build with all temp/cache/artifacts on physical D. Existing CI remains unchanged; Linux/PTY/container/native-human/device/live-provider evidence remains distinct from Windows portable and synthetic tool/helper fixtures.
