### Architect overview

- Inject a separate data message in the protected prefix before frame history at the first Architect request of an active run. Keep that initial snapshot in a bounded in-process cache keyed to the run and workspace so it can remain visible on subsequent turns without rescanning. A new run, root replacement or process restart requires a fresh snapshot. Omit the overview when the request approaches its configured context budget. A failed scan gives an explicit unavailable or partial result and leaves chat usable. Coder and Critic request paths retain their current context.
- Walk deterministic sorted directory prefixes through project-confined filesystem APIs. Cap directory depth at three, traversed directories at 12, encountered directory entries at 256, represented files at 40, and text samples at eight files of at most 8 KiB each (64 KiB aggregate). Cap the projected data at 3,000 UTF-8 bytes and the managed estimate at 1,024 tokens including its label and metadata. Use a 500 ms elapsed scan budget and abort on cancellation. Stop scheduling work on expiry and discard late results. If a directory exceeds its remaining enumeration budget, omit that directory's arbitrary filesystem-order partial results. A fully read directory is sorted before selection.
- Show eligible relative paths and conservative observations from bounded samples, such as recognizable file suffixes, package manifest script names, dependency names, declared entry points or selected declarations/imports. Label names inferred from suffixes and filename conventions. Label partial observations and each skipped category by reason or aggregate count. Absence from the overview gives no evidence that a file, symbol, dependency or test is absent. Manifest declarations establish only what the manifest declares.
- Reuse the existing path confinement and source exclusions, including protected credentials, Git metadata, private controller/provider state, local databases, logs, dependencies and generated outputs. Reject symbolic links, reparse-point aliases, hardlinks, other-device entries and special files. Hold the registered canonical root identity and check it around reads. The overview contains no raw file bodies or absolute paths. Display its content as untrusted data and keep it outside the instruction channel. Ordinary user conversation needs no reconnaissance calls.

### Evidence and admission

- Admit evidence only from successful, complete native results originally delivered by the runtime to the active Architect. A current `read_file` can establish inspected content. A `read_file_range` can establish only the delivered requested lines and whole-file hash. Pagination never attests to unreturned lines and transport truncation disqualifies the result. Directory listings, overview, search or Git results are discovery aids. Add a narrow native path observation for explicitly proposed new files. Prove absence under a safe existing ancestor by a separate authoritative path lookup. Failed, unreadable, excluded, vanished, linked or inaccessible paths do not count as absence.
- Give structural `set_plan` calls temporary per-step admission input containing source references, explicitly new paths, and observable acceptance conditions. Use exact phase/step IDs, relative paths and original native call IDs. Optional symbol claims must be identified by a conservative declaration pattern in the actually delivered text. Imports and dependency claims must cite delivered source, manifest or analogous test/configuration evidence. Persist the accepted structured Plan using its existing revision model. The evidence arguments remain available in the existing native history. Task metadata and prepared Coder context follow in a separate milestone.
- Keep an at-most-32-entry private per-Architect observation window with native tool provenance. Bind entries to the original project ID and registered path/root identity, chat ID, root run and Architect frame IDs, generation and mode version. Store whole-file hash and only the observed span or original native-result reference. Record this binding in the same transition that resolves the native call. Foreign, older-generation, truncated, unobserved, failed and evicted results cannot be substituted by prose, summaries, overview content or a matching path. Restart invalidates any receipt whose original binding cannot be re-established without replay.
- Admission checks are proportional. A single-phase single-step plan with one positively observed file and one observable condition needs only that one inspection and condition. This is the thinnest admissible shape and has no evidence exemption. A new plan must cover each step independently. A later revision can retain existing step definitions and provide evidence for each added, moved or renamed step and for each step in a renamed phase. A removal or reorder of otherwise unchanged steps still needs evidence for a retained step. This lets a large plan grow through bounded revisions while retaining the existing Store progress and goal reconciliation rules. Multiple paths require one verified reference per claimed path. New-file steps require an absence observation for each new path and relevant existing source or a verified empty workspace for genuine greenfield work. The model has no `small`, `skip` or equivalent bypass. The gate checks declared structure and references. It cannot prove all relevant files were disclosed or predict implementation scope from prose.
- Bound admission to eight referenced paths and 16 references per call, at most 256 KiB aggregate distinct-source content revalidation, and 750 ms elapsed validation. Treat limits, unknown freshness and missing scope as a refusal with an actionable request to inspect smaller ranges, re-read current files or split the plan. Bind to exact active call, generation, role, current plan ID/revision/structure, mode, goal revision and registered workspace. Recheck bytes against the original whole-file hash and verify current safe absence during preparation. Recheck root and file identity, absence and call/state bindings at the synchronous `set_plan` commit boundary before revision. An unexpected concurrent external write can happen after the last filesystem observation. Existing file-version/lease controls still govern execution.
- Reuse the existing control/approval/idle/observer/COMMIT/poison guards and goal reconciliation. A refused admission resolves the native tool call as a failure for repair, keeping the plan and its goal requirements/evidence unchanged. It authorizes no delegation, mutation, approval, provisioning or execution. An identical structural no-op uses the same predicate as Store and preserves saved statuses and acceptance. Clearing an existing plan through empty phases proposes no work and retains the prior Store reconciliation and Start building checks. Native deployments use narrowly refreshed storage scopes for overview, observation, evidence rereads and the final synchronous file check and plan transition. Existing plans can still be read and used through their current controls. No migration, second ledger or deployment change.

## Validation plan

Use deterministic temp-project fixtures for scope, secret exclusions, bounds, observation provenance, stale/deleted/changed paths and incomplete reads. Exercise the real Runtime and disk Store for accepted revisions, no-op preservation and refused edits with zero plan or goal changes. Run Node 24 typecheck, focused and full tests, build and applicable existing exact-source CI. Fixture evaluation does not establish local-model or GPU behavior.
